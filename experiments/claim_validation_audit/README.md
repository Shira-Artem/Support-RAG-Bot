# V1.1 — аудит существующего Grounding

Изолированный offline replay 30 сохранённых Model Benchmark ответов и 316 вручную размеченных claim/action меток. **Это измерение адаптера, не фактического production-поведения.** Сеть, Groq, Qdrant, SQLite и production-код не используются и не меняются.

## Воспроизведение

Из корня репозитория с установленными зависимостями проекта:

```powershell
$env:PYTHONIOENCODING='utf-8'
py -3.14 experiments\claim_validation_audit\run.py
```

Скрипт сверяет SHA raw trace с ручной разметкой, все 15 реплик и per-turn evidence с Oracle-сценариями, SHA каждого локального approved-документа и его exact body с сохранённым evidence. Несовпадение останавливает прогон. Источники берутся только из четырёх локальных approved-файлов, перечисленных в `experiments/oracle_rag/cli.py` и сохранённых в `results.json`.

Результаты:

- [report.md](report.md) — метод, матрицы, причины ошибок, архитектурные варианты и следующий gate;
- [summary.json](summary.json) — агрегаты и SHA входов/адаптера;
- [claim-decisions.csv](claim-decisions.csv) / [claim-decisions.json](claim-decisions.json) — все 316 меток, исходная цитата/ручной источник, scope переданного документа и решения двух проверок;
- [errors.md](errors.md) — все 41 расхождение прямого `claim_supported` с ручной разметкой;
- [turn-decisions.json](turn-decisions.json) — диагностические результаты проверки полного ответа на 30 ходах.

Положительный класс — только `supported`: допустимое специализированное утверждение с конкретным переданным approved-источником. `unsupported`, `contradicted`, `potentially_dangerous` — отрицательный класс. `general` (38) не требует профильного источника и исключён из бинарных матриц. Повтор одного утверждения внутри ответа объединён в исходной разметке; повтор в другом ходе остаётся отдельной меткой. 25 цитат встречаются в ответе более одного раза или не привязаны к единственному исходному предложению; их метки сохранены в общих числах и отдельно показаны в sensitivity table. Они требуют ручной проверки span при построении нового датасета.

`claim_supported(quote, exact_evidence, evidence_results=...)` — прямое применение существующей функции к атомарной цитате. Отдельный диагностический столбец применяет `_validation_issue` и `needs_procedure_grounding` к той же цитате с построенным adapter state; эти функции в production получают целый ответ и другую retrieval/state цепочку. Section metadata получены делением exact approved-текста по Markdown `##`, а не из production Qdrant chunks. Поэтому ни один показатель не должен называться частотой пропуска клиентских ответов в Telegram.

Для ручной сверки каждая JSON-строка также содержит до трёх ближайших по словам source clauses (`candidate_source_clauses_not_proof`). Это указатели для рецензента, **не** подтверждение claim и не вход в вычисление метрик. Утверждения об операции, сервисе, оборудовании, отрицании и условии остаются в ручной метке и исходном source; существующий API не выдаёт отдельного проверенного verdict по каждому из этих полей.
