# Oracle RAG: результаты и архитектурное решение

**Дата:** 23.10.2026. **Решение:** **NO-GO** для следующего этапа LLM-first Agentic RAG на текущей `openai/gpt-oss-20b` без отдельной работы над моделью и независимой валидацией утверждений. Oracle evidence снял проблему retrieval для A–C, но модель систематически добавляла несуществующие элементы интерфейса, настройки и полномочия. Production-перенос не выполнялся.

## Условия и воспроизводимость

- До генерации зафиксированы [15 ходов](scenarios.json) и [критерии](criteria.md). CLI проверил четыре локальных approved-документа и все их Qdrant chunks в `knowledge_stage3_retrieval_20261022` (934 points). Сервис каждого документа совпал. SHA исходников/сценариев/критериев, HEAD, точные prompt, история и evidence каждого хода сохранены в [raw trace](results.json). Локальные Markdown содержат тот же смысловой текст, что соответствующие chunks Stage3; Qdrant не изменялся.
- На ход передавались короткий системный prompt, полный последовательный диалог текущего обращения (включая прошлые сырые ответы модели), текущий вопрос и полный approved-текст выбранных статей. DirectBank-документ предоставлялся лишь после подтверждения DirectBank. Для D — без источника; для E — только статья о тарифе ККТ на ходах 2–3. Историю других задач не добавляли.
- Groq `openai/gpt-oss-20b`, effort `medium`, temperature `0.2`, до 3072 completion tokens. **15/15 вызовов успешны**, без повторов. Usage провайдера: **8 689 prompt + 6 030 completion = 14 719 токенов**, из них 2 804 reasoning. Сумма собственно HTTP latency **22,237 с**, медиана **1,323 с** (1,062–2,200 с); это не wall time прогона: между вызовами было pacing 18 с.
- Исходные ответы не менялись оценкой. [scorecard](scorecard.json) создан после генерации; [reviewed trace](reviewed-results.json) содержит восемь осей оценки, причины и SHA исходного текста по ходу. Полные реальные ответы приведены там дословно. В `results.json` хранятся также prompt и причины provider errors (их не было).
- Независимый post-review помечает ответы с неподтверждёнными фактами или safety-провалом как `blocked_unverified_or_unsafe`; это исследовательский trace, ни один из ответов не выдавался клиенту. Эта пометка не переписывает raw answer.

Показательные дословные фрагменты ответов (полный текст каждого хода в `reviewed-results.json`):

> **A3:** «В „Сервис → Настройки → Банки → DirectBank“ найдите раздел „Счета“… Если какой-то счёт пропущен, добавьте его вручную.» Источник подтверждает только сверку списка счетов с настройкой обмена; такого меню и изменения счета не содержит.

> **B3:** «Если чек пробили вчера… Дата начала – 27 ноября 2024». Основное правило по дате пробития верно, но пример несовместим с датой эксперимента 23.10.2026. Модель также обещает, что чек «будет найден» без доказательства передачи чека.

> **C3:** «роль … обычно называется „Просмотрщик“ (или „Viewer“)». Источник прямо не устанавливает название роли и матрицу прав.

> **D3:** «уточните … тип накопителя … цель изменения». Эти сведения уже дважды обозначены неизвестными. Пошагового изменения модель не дала.

> **E2:** «в кабинете Платформы ОФД вы можете увидеть актуальный статус и срок оплаченного периода тарифного ключа». Переданная статья описывает оплату/активацию для ККТ, но не подтверждает это поле или срок.

Ручная оценка по 15 ходам: понимание задачи **15/15**, удержание контекста **10/10 применимых**, соответствие теме **15/15**. Конкретная полезность **5/15**, подтверждение фактов **2/13 применимых**, отсутствие опасных/выдуманных инструкций **12/15**, качественное уточнение **1/7 применимых**, обоснованная эскалация **0/4 применимых**. Это качественная рубрика малого набора, не статистика для всех запросов. [Постатрочная таблица](score-table.md) и причины в trace.

## Причины, baseline и пределы сравнения

**Модель.** Понимает естественный запрос и держит тему через уточнения без LexicalAnalyzer/operation gates. Критическая слабость — переход от правильного источника к правдоподобным, но неподтверждённым конкретным деталям. Сильнее всего видна в A3 и C2–C3. Также не выполняет мягкое правило одного вопроса, повторяет закрытые неизвестные слоты и не выбирает эскалацию. B3 показывает ошибку обычного временного рассуждения. Увеличение prompt с тем же источником само по себе проблему не решило.

**Данные/retrieval.** Для A–C источники корректны и напрямую предоставлены модели: их провал уже нельзя объяснить низким dense rank. Для D отсутствуют конкретная операция/модель и применимая approved-процедура; здесь safe clarification нужна. Для E статья о тарифе не содержит юридического срока договора или даты оплаченного периода; недостаток знаний — самостоятельное ограничение. Модель дополнительно неверно расширила этот источник. Набор не проверяет способность нового retrieval выбирать документы.

**Исторический baseline.** В [сохранённом vNext отчёте](../vnext/report.md) на других 15 ходах/7 сценариях старый offline pipeline решил 0/5 исходных проблем, дал 2/2 частично полезных положительных контролей с ошибками; vNext решил 0/5 и 0/2 контролей. vNext потребил 20 вызовов/30 316 токенов, baseline — 6/11 295. Oracle получил 0/5 по строгому решению, 15/14 719; это **не A/B**: здесь три хода в каждом из пяти сценариев, заранее правильные полные документы, другая генерация/prompt, текущий локальный snapshot с незакоммиченными P0.3/P0.4, другой runtime/pacing. Сравнение показывает тип отказов, а не величину улучшения.

## Ответы на архитектурные вопросы

1. GPT-OSS 20B распознала все пять задач и последующие уточнения. Понимание темы было сильнее процедурной точности.
2. Исходная задача сохранена на 10/10 следующих ходах. Однако память о *том, что клиент не знает* модель использовала плохо на D; контекст не равен качественному следующему действию.
3. Без старых ранних gates модель дала документированные элементы A–C; вместе с ними выдала неподтверждённые, иногда изменяющие конфигурацию шаги. Самостоятельный ответ без защищающего слоя недостаточен.
4. Модельные ошибки: галлюцинация UI/ролей/матрицы, избыточные вопросы, неверная временная дата, чрезмерные обещания результата, отсутствие эскалации.
5. Retrieval не является причиной отказа A–C в oracle-условиях. Реальный пробел знаний E и неопределённость D остаются даже при идеальном выборе источника.
6. Сохранить approved и scope-проверки, запрет неподтверждённой опасной операции, проверку каждого утверждения/шага и отдельное решение об эскалации. Старые ранние lexical/task gates и extractive rewrite вероятно избыточны для понимания/памяти, но их удаление нельзя считать безопасным по этому прогону; нужен иной надёжный safety/grounding слой без скрытой правки ответа.
7. **NO-GO** к реализации `LLM Understanding → Task Memory → Hybrid Retrieval → Evidence Selection → LLM Decision/Answer → Safety Validation` сейчас. Гипотеза понимания подтверждена, гипотеза достаточной доказательной генерации опровергнута на контролях. Схема остаётся исследовательской, следующий этап автоматически не реализован.
8. Текущей модели недостаточно для самостоятельной проверяемой техподдержки. Следующая проверка — отдельный model benchmark на тех же зафиксированных oracle inputs и source-level оценке шагов (либо изолированное исследование поствалидации), прежде чем принимать решение о миграции. Малый набор не доказывает, что другая модель обязательно лучше.

## Ограничения

Сценарии синтетические, evidence выбран вручную, документы локальные и ранее одобренные; актуальность внешних страниц заново не устанавливалась. Source hashes и Qdrant status сверены, но этот прогон не является тестом production SQLite, Telegram, живых клиентов или юридической достоверности договора. Оценки выставлены вручную после генерации по заранее записанной рубрике; отдельного второго эксперта не было. Старые изменения рабочего дерева сохранены, commit/push и production-записи не выполнялись.
