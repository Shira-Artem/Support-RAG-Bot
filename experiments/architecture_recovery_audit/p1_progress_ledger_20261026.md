# P1 D2 — ProgressLedger offline E2E

Дата: 2026-10-26. Checkout: `main`, стартовый `HEAD 54ea1b9ada69ca103fae3210b035972777b80183`, рабочее дерево чистое. Статус: **offline реализация выполнена; live/worker/production NO-GO**.

## Реализация

В существующий `TaskContext` добавлены `procedure_id`, проверенные source-backed `shown_units`, `eligible_units`, `checks`, `open_question`, `current_subgoal`, счётчик уточнений и флаг `closed`. JSON schema v2 и SQLite-таблицы не менялись; новые поля additive и читаются с defaults из старых snapshot-ов.

`DialogueManager` — единственный автор статусов результата. Его reducer сопоставляет сообщение клиента с units из локально проверенного approved-раздела, сохраняет точную цитату и её span, различает `asked`, `passed`, `failed`, `unknown`, `not_done`. Положительный ответ бота заносит unit как показанный/заданный, но не завершённый. Противоречащие друг другу положительный и отрицательный отчёты дают `unknown` с обеими цитатами. Проверенные user outcomes продолжают technical-action route; ожидаемый model scope остаётся открытым, пока клиент не назовёт модель.

Для Эвотор технический ответ регистрирует номера шагов только из exact section после approved/status/SHA проверок. Если модель неизвестна, код сохраняет безопасный предварительный шаг и не публикует меню для конкретных моделей. После результата проверок он кратко сообщает сохранённые результаты и объясняет, что следующая применимая часть зависит от модели; без новых результатов повторное общее уточнение не задаётся.

Общая семантика завершения закрывает активную задачу и очищает open question. Новый технический запрос после завершения создаёт новый task. Распознание использует общий набор форм завершения/благодарности, а не одну контрольную фразу.

## Сопоставимый диалог

Оба плеча прошли через настоящий `bot.handle_message`, `ConversationStore`, reducer и временную SQLite с новым `ConversationStore`/close/reopen на каждом ходе. Retrieval использовал настоящий локальный `RetrievalPipeline` и один локальный approved-документ `evotor/ofd/ofd-unable-to-connect.md`; Understanding, planner/composer и Qdrant transport были offline fixture/mocks. Реальных Groq, Qdrant network, Telegram, worker или production database calls не было.

Входные реплики в обоих плечах одинаковы:

1. «Эвотор, чеки не уходят»
2. «Интернет работает»
3. «Оплату проверил»
4. «Что дальше?»

**OLD** — тот же Source-first baseline с `AI_COORDINATOR_ENABLED=0`. **LEDGER** — coordinator technical-action + ProgressLedger. Первый точный approved ответ совпал в обоих плечах:

## Negative gates и проверки

- Отрицательный исход «Интернет не работает» → `failed`; «Интернет не знаю» → `unknown`; «Интернет пока не проверял» → `not_done`.
- Противоречие «Интернет не работает» → «Интернет работает» сохраняет оба exact spans и переводит check в `unknown`.
- В первом ходе только рекомендация бота оставляет result как `asked`, не `passed`. «Оплату проверил» остаётся `unknown`; отдельный replay с явным «Оплата прошла» даёт `passed`.
- Неизвестная модель удерживает модельную процедуру и меню; данные проверки и вопрос scope переживают SQLite reopen.
- «Спасибо, всё решено» закрывает task без retrieval/диагностики; следующий вопрос про 1С создаёт новую задачу.
- Существующие safety regressions S1/S4/S5 продолжают проверять опасную операцию, чужую инструкцию и injected source content через `bot.handle_message`.
- Целевой набор `python -m pytest tests/test_telegram_pilot_sqlite_replay.py -k "progress_ledger or d14_closes" -q`: **8 passed**.
- Полный `python -m pytest -q`: **428 passed, 5 xfailed, 13 warnings, 0 failed** (44.68 s). Один прежний strict xfail по закрытию стал обычным passing тестом; оставшиеся пять xfail не изменены.

## Ограничения и следующий шаг

Это offline evidence-bound вертикаль на сохранённых understanding fixtures и одном approved документе, а не доказательство live Groq/Qdrant качества. Понимание результата пока ограничено лексическими формами, связанными с текущими exact approved units; широкая оценка paraphrase coverage и независимый holdout не выполнялись. В данном кейсе инструкция сама требует модель до перехода к следующим пунктам, поэтому система корректно остановилась на сборе модели, а не выдала не применимую процедуру.

P1 D2: **OFFLINE DONE** только в проверенной вертикали; **LIVE BLOCKED / не запускался**, **PRODUCTION NO-GO**. B2 default-off/NO-GO. Retrieval filters, KB, Qdrant, `.env`, production SQLite, Telegram worker и handoff branch не менялись. Реальные Groq/Qdrant SHA/результаты для D2 неприменимы: сетевые вызовы не делались. Следующий утверждённый этап — handoff integration readiness в отдельном worktree от актуального main; live Telegram/worker и merge/push интеграции запрещены без отдельного разрешения.
