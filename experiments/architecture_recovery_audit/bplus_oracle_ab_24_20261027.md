# B+ — архитектурный A/B-аудит выбора технического evidence (27.10.2026)

**Статус: завершён; production NO-GO и без изменений.** Проверялась, а не предполагалась гипотеза, что Hybrid находит источники, но task/operation и lexical evidence мешают ответу.

## Метод и границы

- 24 frozen попытки; KB grade A=13, B=9, C=2. #11 unreplayable из-за исходного Understanding HTTP 400; ничего не реконструировалось.
- A — текущий Resolver + Evidence Gate; B — expert task/operation override + read-only Stage3 retrieval; C — экспертно заданный approved section через тот же SourceFirst/SHA/scope/safety/renderer; D — три real Groq ID-only calls на двух кейсах.
- A/B/C: ноль Groq, одинаковый локальный deterministic planner fixture. Метрики относятся к локальному pipeline, не live-answer model. C — oracle upper bound.
- D: модель `openai/gpt-oss-20b`; HTTP 200×3, HTTP 400/429×0, retry×0; 3,643 tokens / 2,737 ms. Небольшой направленный sample, не benchmark. A per-case offline latency и нулевые provider tokens сохранены в JSON (median 608 ms по 23 replayable из предыдущего frozen report); B/C provider tokens также 0, их per-case latency в этих harness runs не instrumented.
- Production code, KB, Qdrant, SQLite, `.env`, worker не менялись. Stage3 read-only; коммит и публикация не входили в эксперимент. Последующий push этого отчёта выполняется по отдельному прямому запросу пользователя. [Обезличенная матрица ответов](../experiments/architecture_recovery_audit/bplus_oracle_ab_24_20261027.json).

## Причинная матрица

| Этап | Доказательство | Вывод |
|---|---|---|
| Understanding | Expert labels меняют candidate sets в основном #3/#7/#8/#18/#23. #11 остаётся HTTP 400. | Task oracle увеличил полезность лишь 5→6/13: смысловое понимание — вклад, но не главный общий bottleneck. |
| Retrieval | B имеет selected candidate в 19/23, но #23 нерелевантен; #22 с Oracle integration/API task остаётся без selected candidate из-за `subtask_anchor_uncovered`. | «Документ попал в candidates» недостаточно. Гипотеза Hybrid-попадания частично подтверждена, не универсально. |
| Evidence | C даёт 5→7/13. D #24 проходит с цельным разделом; D #9 верный раздел останавливает отдельный несовместимый service-slot validator. | Самое сильное свидетельство за evidence selection/contract alignment, без основания ослаблять scope. |
| Answer / State | B/C с подходящим разделом по-прежнему возвращают #5/#6/#18 `progress_ledger_waiting_for_model`; #7/#8 требуют отсутствующую модель. | Есть post-retrieval State blockers и легитимные applicability clarifications. Renderer exact-copy не первопричина, когда есть правильный approved section. |

### Гипотеза

- Частично подтверждена: Oracle Task дал +1 полезный A из 13, Oracle Evidence — +2. Candidate hit (19/23) далеко не равен полезному ответу.
- Сильная версия “Hybrid всегда находит” не подтверждена: #22 matching отсекает подходящую тему, #24 A выбрал status вместо поиска, #23 допускает соседнюю тему. State и scope тоже блокируют.
- Реальный false refusal: D #9 — SourceFirst accepts confirmed aQsi manufacturer, отдельный selector validator требует `service`. Model requirements в #7/#8 не называются ложным отказом.

## Предыдущие Oracle/selector эксперименты

- Oracle RAG free-form: 0/5 полезных из-за выдуманных UI/ролей/операций. C не генерирует инструкцию: только подстановка approved section, далее существующий безопасный pipeline; это upper bound, не повтор той схемы.
- Старый ID-only selector: 3 полезных outputs из 3 успешных calls, один 429 из четырёх попыток на другой малой выборке. Здесь D ограничен approved/scope-compatible кусками и выводит ID+facet; после этого локальная проверка и точный approved text. Результат снижает hallucination surface, но выявляет indivisible procedure block и несовпадающие scope contracts. 3 вызова не статистически достаточны.

## Решение

- Наибольшая oracle верхняя граница — C: **7/13 A**; это не deployable selector.
- **LLM Evidence Selector: NO-GO для внедрения и Telegram-пилота.** Всего 2 вопроса; один полезный, другой false-refused, а #24 потребовал изменить prompt после первого отказа.
- Минимальный следующий кандидат: selector validator должен повторно применять текущую SourceFirst scope-compatibility policy вместо дублирующей более строгой service-slot проверки. Оставить service/model/version checks, SHA/approved gates и один цельный section. Код не менять до согласования.
- Worker не переключался; Telegram pilot не выполнялся. Не переходить к реализации автоматически.
