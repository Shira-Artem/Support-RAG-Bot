# P0.3 — граница источника и безопасный частичный ответ

Дата: 2026-10-25. [План](implementation_plan.md), [P0.2 baseline](p02_report.md), [текущая шестиходовая SQLite трасса](sqlite_bot_replay_20261025.json), [E2E тест](../../tests/test_telegram_pilot_sqlite_replay.py). Работа выполнена offline в текущем дереве; Qdrant candidate source, Groq и Telegram I/O подменены. Approved Markdown читается и сверяется локально, но база знаний и индекс не менялись.

## Причины и решение

| Задача | До P0.3 | После P0.3 |
|---|---|---|
| Поиск чека по номеру ФН без названия ОФД | Правильный новый `receipt/search` task и применимая по задаче approved статья Платформы ОФД доходили до второго `source_scope_context_missing`. Ограничение «ФН не подтверждён как прямой фильтр чеков» не становилось ответом. | Source-first допускает **только информационный отрицательный факт** из task-matched approved раздела «Ограничения», если это единственный подходящий документ, в вопросе совпадает конкретный предмет ограничения, а раздел не содержит процедурного/interface утверждения. Ответ дословно цитирует весь раздел с названием сервиса и явным «ваш сервис пока не подтверждён». SHA и heading повторно проверяются перед выдачей. Новый route `answer/source_first_scoped_limitation`; техническая процедура при отсутствии service остаётся заблокированной. |
| Эвотор, чеки не передаются, модель неизвестна | Exact renderer выдавал всю «Безопасные проверки», включая меню для конкретных моделей 5/7.2/7.3/10/Power и поля EoU, хотя модель не подтверждена. Формулировка была условной, но нарушала цель не показывать device-specific шаг до подтверждения модели. | Из пронумерованной approved секции публикуется только первый независимый preflight, который явно устанавливает недостающую модель и не содержит interface-действия; отдельно сохраняются проверенные безопасные предупреждения. В данном replay это «Выясните модель Эвотора и проверьте действительность оплаченного периода…». Меню и проверка EoU не выдаются. Если такого первого шага нет, ответ уточняет модель. После первого ответа прежний P0.2 no-repeat gate работает на частичном тексте. |

Это общий контракт для source-attributed limitation и первого независимого шага. Никакой вывод о *всех* ОФД из отсутствия поля в одной статье не делается. Наличие слова «ФН» само по себе не создаёт маршрут: нужен task-matched approved hit, явное отрицательное утверждение в разделе, совпадение предмета и отсутствие действий. Для незнакомого сервиса всё ещё запрещено переносить меню Платформы ОФД.

## Измерение и отрицательные случаи

Шесть исходных ходов после P0.3: `clarify`, grounded `answer`, безопасный частичный `answer/source_first_safe_preflight`, `clarify/equipment`, bounded `escalate`, scoped `answer/source_first_scoped_limitation`. Ход 6 больше не xfail; проверка его содержания, области, отсутствия меню и отсутствия вызова модели осталась отдельным passing assertion. Ходы 3–5 не повторяют конечный текст, SQLite повторно открывается на каждом ходе, user fact provenance и state восстановление проходят.

- Независимый bot/SQLite сценарий с ФД при неизвестном сервисе не получает ограничение для ФН. Сценарий с подтверждённым aQsi Online не получает ограничение Платформы ОФД. Existing foreign-service/applicability tests сохраняются.
- Ограничение с добавленной процедурой отвергается. Unconfirmed model не открывает model-specific меню, даже если оно находится в том же approved разделе; отсутствие безопасного preflight оставляет clarification. Опасное закрытие архива ФН по-прежнему эскалируется до retrieval/LLM.
- Full pytest после P0.3: **390 passed, 0 failed, 13 warnings** (`python -m pytest -q --disable-warnings`). До P0.3: **385 passed, 1 strict xfailed, 13 warnings**. Профильный offline E2E: **114 passed**. `git diff --check` выполнен без whitespace errors (Git вывел только предупреждения LF/CRLF).

## Решение и предел

**P0.3 DONE offline**, при выполнении финальных проверок выше. Исторический ручной Telegram-пилот и его 0/6 не пересматриваются по результату fixture. Уверенность в выборе реального Qdrant/Planner и полезности новых формулировок без live provider не измерена. Следующий шаг по roadmap — отдельный offline quality/safety gate на D1–D3 и один bounded live-path прогон; worker switch и ручной Telegram retest требуют отдельной проверки loaded runtime SHA/allowlist и согласования. Команда на commit/push получена от пользователя в этом ходе; она относится к актуальному коду и отчётам после проверок, а не к запуску P0.5 или обновлению worker.
