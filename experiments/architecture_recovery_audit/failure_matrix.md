# Матрица отказов и воспроизведённых регрессий

Дата: 2026-10-25. Факт из пилота = сохранённая обезличенная диагностика [PROJECT_STATE](../../docs/PROJECT_STATE.md). Кодовое объяснение = проверено по файлам в рабочем дереве; незакоммиченные правки явно помечены. Результат тестов: `python -m pytest -q --disable-warnings` → **376 passed, 5 failed, 13 warnings** (15.38 s). У теста есть право проверять поведение, но само ожидание не является доказательством правильной архитектуры.

Сохранённые field diagnostics подтверждают validated значения, но raw provider JSON для этих шести ходов не найден. Не приписываем модели дословные поля, не сохранённые в трассе. Ноль полезных ответов — оценка ручного пилота пользователя, а не автоматическая метрика на всём трафике.

Классы **3. окружение** и **4. пока неизвестно** к этим пяти terminal assertions не применены: все пять стабильно повторились локально, без сети. Для второго падения точная промежуточная причина `rejected` остаётся недиагностированной; это ограничение причинной детализации, не основание объявить его окружением. `git diff` показывает, что четыре первых пути (lexical/legacy) не затронуты текущими semantic правками; пятое ожидание не менялось в `HEAD`, а новая retrieval ветка не активна для фактического state. Полный baseline suite на чистом `HEAD` не запускался, поэтому «существовал до правок» следует из неизменности исполняемой ветки и сравнения кода, а не из отдельного baseline run.

## Почему зелёные тесты не предсказали пилот

1. Успешный двухходовый E2E проверял два объяснения об ОФД, но не broad greeting, diagnosis, unknown intent, pending service или смену task. Его 9 LLM-вызовов/13 352 токена не показывали поведение смешанной переписки.
2. Большая часть offline проверок напрямую конструирует `DialogueState`, `Observation` или fake retrieval/generation. Они обходят `bot.py → Understanding → SQLite persist/replay → SourceFirstService`. `scripts/replay_incident.py` использует lexical state и записанные ответы; это иной путь.
3. Реальный provider дал допустимую по схеме, но семантически неполную комбинацию `unknown intent / explain`; cross-field gate воспринял её как technical scope. Для симптомов и clarification relation были другие неожиданные допустимые значения. Тесты слишком часто проверяли идеальную комбинацию полей.
4. Offline pass rate не является метрикой «полезный ответ на каждый ход». Повтор вопроса и отсутствие безопасной частичной диагностики могли быть корректными по отдельным локальным инвариантам.
5. После новых локальных правок live и SQLite-backed path не прогонялись; worker PID 46544 использует предыдущий loaded snapshot. Сравнивать его Telegram ответы с новым деревом нельзя.

Следующее доказательство должно быть сквозным: см. [acceptance_scenarios.md](acceptance_scenarios.md). Для изолированной SQLite тест должен вызывать **именно** `bot.handle_message` с fake Telegram update, подменёнными сетевыми границами и настоящим `ConversationStore`, включая повторное создание store между ходами. Нельзя передавать в `SourceFirstService` заранее идеальный state.
