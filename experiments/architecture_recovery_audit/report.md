# Глобальный архитектурный аудит Support-RAG-Bot

Дата: 2026-10-25. Область: текущий `main` (`39df63c`) с уже существовавшими незакоммиченными правками. Аудит не менял production-код, тесты, знания, Qdrant, пользовательскую SQLite, `.env` или Telegram worker. Источники фактов: исполняемый код по ссылкам ниже, локальные approved-статьи, сохранённые результаты и воспроизведённый offline suite. Реальные шесть реплик взяты из ранее сохранённой обезличенной диагностики в [PROJECT_STATE](../../docs/PROJECT_STATE.md); приватные строки SQLite заново не выгружались. Внешнюю актуальность статей и live качество текущего дерева этот аудит не проверял.

## Вывод

Source-first содержит полезное безопасное ядро: approved/scope фильтрацию, проверку локального SHA, запрет необратимых операций и дословную выдачу технических разделов. Текущая **оркестрация чрезмерно сложна для повседневного разговора**. Она требует согласованных `request_type`/`intent`/`operation`/`task_category`/`scope`, затем до пяти последовательных LLM-решений для простого объяснения. Отказ любого звена часто превращает безопасный общий вопрос в эскалацию. Шесть реальных Telegram-реплик дали 0 полезных ответов; двухходовая демонстрация не покрывала этих путей. Рекомендуется вариант **B: один разговорный координатор с явным разделением общего разговора, проверяемых информационных ответов и технического RAG**, при сохранении существующих safety gates. Это решение об архитектурном направлении, не разрешение на реализацию другого этапа или обновление worker. Подробности в [decision.md](decision.md).

## Реальный путь сообщения

```text
bot.py: режим/allowlist
  → ConversationStore.history + dialogue_state (SQLite replay)
  → Groq Understanding (для Source-first; 1 вызов)
  → ConversationStore.begin: persist validated Understanding
  → ConversationStore._sync_state → DialogueManager.advance
  → SourceFirstService.answer: social/incomplete/risk gates
  → build_rag_query → Retriever (Qdrant dense + локальный BM25 + RRF)
  → RetrievalPipeline: task, operation, approved, applicability
  → local approved source/section/SHA check → второй source scope gate
  → Planner (1 вызов) → exact-source renderer ИЛИ Composer (1 вызов)
  → claim_supported + procedure checks → при отказе Repair (до 1 вызова)
  → Semantic Judge (1–2 вызова по ветке) → ConversationStore.complete
  → Telegram reply или кнопка заявки специалисту
```

Код: [bot.py](../../bot.py) `handle_message`; [conversation_store.py](../../app/conversation_store.py) `_sync_state/begin/history`; [dialogue_understanding.py](../../app/dialogue_understanding.py) `validate_response/understand_message`; [dialogue_state.py](../../app/dialogue_state.py) `advance/observe_answer`; [retrieval.py](../../app/retrieval.py) `Retriever.search`; [retrieval_pipeline.py](../../app/retrieval_pipeline.py) `search`; [source_first_service.py](../../app/source_first_service.py) `answer`. Возможность обратиться к специалисту в [bot.py](../../bot.py) `free_callback`; текст Source-first честно говорит, что доставка сотруднику ещё не настроена. «Эскалация» в генерации означает ответ с кнопкой/локальной заявкой, не доказанную доставку человеку.

## Что необходимо и где теряется полезность

| Компонент | Сохранить / изменить | Фактическая роль и проблема |
|---|---|---|
| ConversationStore + task memory | Сохранить, упростить контракт | Только здесь закрепляются клиентские факты и `expected`; assistant-факты не принимаются за клиентские. Ранее `answer_to_clarification` снимал слот без значения; текущая незакоммиченная семантическая защита покрывает лишь часть путей. |
| Understanding | Сохранить распознавание смысла, снять роль единой точки отказа | Строгая схема и exact-span доказательство фактов полезны. Но пропуски семантических labels превращались в `unknown`; ошибка вызова ведёт к немедленной эскалации. Один вызов нужен только при содержательной реплике или неясной связи. |
| Retrieval + approved/applicability | Сохранить для технических фактов | Отдельные taxonomies/эвристики в Understanding, DialogueState, RetrievalPipeline и Source-first расходятся. Категория может быть не определена даже при релевантной статье. |
| Второй source scope gate | Объединить с retrieval applicability | Повторно проверяет почти те же service/manufacturer/model, но трактует каждую секцию как процедуру, кроме узкого `general/explain`; здесь блокировались определение ОФД, диагностика Эвотор и ограничение поиска по ФН. |
| Planner + selected section | Сохранить выбор evidence для техник; проверять область | Один раздел снижает риск сборки несовместимых процедур, но может скрыть безопасную диагностическую часть, условия соседнего раздела и ответ на общий вопрос. `_source_sections` ограничивает ввод четырьмя секциями. |
| Exact-source renderer | Сохранить для процедур после проверки порядка/условий | Модель не дописывает шаги. Целая секция не гарантирует порядок предупреждения и применимость пользователю. |
| Composer + Grounding + Repair + Judge | Разделить safety и quality, сократить цепочку | Composer есть только для `general/explain`; `claim_supported` проверяет предложения, Repair генерирует повторно, Judge оценивает релевантность только выбранному фрагменту. Это несколько потенциальных отказов и повторное чтение того же evidence. Judge не доказывает entailment, Grounding не доказывает ответ на вопрос. |

## Разговорное поведение по коду и наблюдениям

| Ситуация | Текущее поведение / предел доказательства |
|---|---|
| Чистое приветствие | `request_type=greeting` даёт короткий ответ до RAG. Смешанное «Привет! Помоги…» в пилоте пришло как `information/explain`, дошло до retrieval и эскалации. Текущая правка broad explanation просит задачу; live не проверена. |
| Простое определение | Для `general/explain` разрешён информационный путь. В пилоте `intent=unknown`, поэтому scope gate потребовал service. Локальная правка нормализует explain → general; есть риск слишком широко считать всякое «объясни как» общим определением. |
| Самостоятельный новый вопрос / смена темы | `relation=new_task` создаёт новый task и сохраняет session entities отдельно; соответствующее состояние в шестом ходе сменилось. Но scope source всё равно потребовал сервис для ответа о границе поиска по ФН. |
| Продолжение и местоименная ссылка | Reducer хранит task/object и `object_reference`; предыдущий двухходовый E2E это подтвердил для ОФД. Отдельный падший lexical test по сроку договора показывает ошибочное создание нового task. Production semantic follow-ups шире не доказаны. |
| Ответ на уточнение | `expected` и exact клиентские entities должны закрывать слот. В пилоте модель назвала новый вопрос ответом на уточнение и слот исчез без service. Незакоммиченная правка удерживает entity slot в semantic пути, но lexical тест с «Мой ОФД?» всё ещё падает. |
| Новая информация без ответа на слот | Симптом/цель накапливаются в task. Source-first повторял service вопрос; теперь незакоммиченная ветка меняет формулировку, но всё ещё не предлагает подтверждённую общую проверку и не устраняет зависимость от service. |
| Смена оборудования/сервиса | Есть отдельные session/task route и сброс equipment при смене производителя. Нужны многоходовые проверки на несовместимые атрибуты; зелёный unit-тест не подтверждает Telegram путь. |
| Завершение и возобновление | `classify_user_turn`, `observe_answer`, кнопка «Новый диалог» существуют. Нет проверенного сквозного сценария закрытия/возобновления активной задачи через SQLite и Telegram. |
| Эскалация | Риск операции и отсутствие approved evidence должны приводить к безопасному отказу. Для общей справки и частичных безопасных проверок текущая эскалация избыточна. |

## Retrieval и знания

`Retriever.search` получает dense top-N из Qdrant, строит BM25 по всем разрешённым points локально, сливает RRF, проверяет точные коды ошибок/модели. `RetrievalPipeline` повторно требует approved, task/operation и applicability, разворачивает sibling chunks только после отбора статьи. `Chunker` режет Markdown по `##`, затем по абзацам/лимиту 1200 символов; источник информации может оказаться отдельным question-only chunk. `SourceFirstService` восстанавливает до четырёх exact sections по локальным Markdown и SHA. Это объясняет, почему raw попадание документа ещё не означает полезного ответа.

Read-only инвентаризация `data/knowledge/*.md`: **206 approved, 63 draft**; approved распределены по восьми корневым разделам. Доступны `atol_online/ofd/what-is-ofd.md`, `evotor/ofd/ofd-unable-to-connect.md`, `platformaofd/ofd/lkk-receipt-search.md`. Первая статья подтверждает общую роль ОФД, но помечена scope АТОЛ Онлайн; вторая содержит первичные проверки Эвотор и предупреждение; третья прямо говорит, что ФН не подтверждён как прямой фильтр **в Платформе ОФД**, а не во всех сервисах. Для универсального категорического «по ФН нельзя» этих данных недостаточно. Отсутствие полной базы общих нейтральных определений и частичных диагностических карточек — установленный пробел покрытия, а не доказательство, что все 206 статей бесполезны.

Исторический [Stage 3 retrieval report](../../reports/stage3/README.md) на 83 approved-reference вопросах: top-5 61/83, pipeline selected 40/83; 31 reference случая тогда оставались `task_unresolved`. Это offline измерение прежнего корпуса/кода, не показатель текущего Telegram качества. В [Oracle RAG](../oracle_rag/report.md) правильно выбранные источники не предотвратили выдуманные шаги. Следовательно, требуется отдельно мерить recall, применимость, качество содержания и финальный ответ.

## Grounding и стоимость

`_validate_information_composition` отклоняет всё объяснение, если хотя бы одно предложение не проходит эвристический `claim_supported`; сохранённый Q2 показывал одну подтверждённую и одну неподтверждённую фразу. Ограниченное partial acceptance добавлено, но проходит только для двух независимых предложений, с проверкой условий и новым Judge. `unsupported_information_claim` — не единая причина: возможно реальная галлюцинация, парафразный false reject или потеря условия. Без per-claim разбора нельзя автоматически ослаблять guard. Judge проверяет «отвечает ли вопросу» и ID реальных фрагментов, но только внутри выбранной секции; неправильный выбор источника он может отклонить, однако не вернуть систему к следующей секции. Repair может улучшить ответ, но добавляет ещё генерацию и ошибку. Точный ledger из [V1.1](../claim_validation_audit/report.md): helper имел 30 FP, включая 2 опасных; [Typed replay](../typed_claim_validator/report.md) закрыл опасные FP ценой 0/56 принятых правильных claims. Поэтому safety не отключать.

Последний ограниченный двухходовый успешный live [журнал](../../docs/PROJECT_STATE.md) зафиксировал 9 LLM-вызовов и 13 352 токена, не типичную стоимость всех запросов. Предыдущий Q1/Q2 прогон после Repair имел 12 979 токенов и полный отказ Q2. Контракт позволяет информационной реплике 1 Understanding + 1 Planner + 1 Composer + 1 Repair + 1 Judge; фактическое число зависит от ветки. Серийные сетевые вызовы и повторная передача task/sections объясняют задержку и риск 429; экономию будущего варианта нужно измерить, не предполагать.

## Source-first и legacy

Legacy [answer_service.py](../../app/answer_service.py) умеет pre-retrieval greeting/thanks/capabilities/vague-help, частичное использование evidence, deterministic `repair_response`, notice о неполном покрытии и контекст пользователя. Source-first сильнее в source provenance: LLM не пишет технические шаги, approved source перечитывается по SHA, выбранная секция проверяется точно. При переходе потеряна полезная legacy идея **частичного ответа/coverage notice для неинформационных задач** и ранний широкий social route не сработал при смешанной реплике. Legacy не готов как безопасный откат: Oracle и сохранённые ответы показывают неподтверждённые шаги; один из текущих legacy тестов тоже падает. Нужен перенос механизмов, а не переключение всего бота назад.

## Прямые ответы на семь вопросов

1. **Почему тесты были зелёными, а Telegram не работал?** Успешный узкий E2E не включал шесть реальных форм обращения и не шёл через весь `bot.py`/SQLite replay. Он тестировал выбранную комбинацию Understanding labels; реальный provider дал другие валидные, но неполные комбинации. Большая часть unit проверяла изолированные стадии. Теперь и полный suite имеет пять падений, см. [матрицу](failure_matrix.md).
2. **Пригоден ли pipeline?** Его approved/exact-source техническое ядро пригодно; единая жёсткая цепочка для всех речевых актов чрезмерна и не прошла ручной quality gate.
3. **Что менять?** Единый task/slot контракт, разделение information/technical applicability, полезную частичную помощь и измеряемую route policy; затем убрать дублирующие проверки на основе парных данных.
4. **Разделять обычный LLM-диалог и технический RAG?** Да, по типу утверждений и риску. Простая беседа и формулировка задачи не требуют технического retrieval; любые конкретные доменные факты и действия требуют соответствующего evidence/safety.
5. **Один вариант?** B — разговорный координатор с отдельными маршрутами, существующим approved RAG и независимой защитой технических действий.
6. **Первые три изменения?** Сквозной SQLite-backed replay через `bot.handle_message`; исправление task/expected/routing; отдельный scope policy для ограничений/безопасной диагностики и процедур. Измерение на [21 реплике](acceptance_scenarios.md) и шести safety negatives.
7. **Что нужно перед повторным ручным Telegram-тестом?** Зелёный offline safety и сквозной route gate, один ограниченный live-path прогон с токенами и ответами, затем отдельное разрешённое обновление worker с проверкой PID, receipt/source SHA и allowlist. Отказ может быть безопасным в диагностике, но неподтверждённое действие блокирует пилот.

## Границы аудита

Не проведены новый live E2E, Telegram-пилот, доступ к внешней актуальности документации и сравнение обеих архитектур на одном holdout. Текущий PID 46544 найден живым; runtime receipt содержит прежний Source-first SHA `4a98…147`, текущий файл имеет `173b…32b`. Это подтверждает различие source snapshot и рабочего дерева, но не тестирует поведение процесса в реальном времени. Причины и классификация тестов — [failure_matrix.md](failure_matrix.md), варианты — [alternatives.md](alternatives.md), программа — [implementation_plan.md](implementation_plan.md), критерии — [acceptance_scenarios.md](acceptance_scenarios.md).
