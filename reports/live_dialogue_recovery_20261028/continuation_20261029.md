# Продолжение 29 октября: память порядка и воспроизведённый отказ Groq

**NO-GO для Telegram-worker.** Причина следующего отказа теперь установлена точнее: идентичный strict-schema запрос Understanding иногда получает HTTP400 с синтаксически повреждённым JSON провайдера. Последний полный контроль остановлен также дневным лимитом TPD. Worker не запускался; Qdrant работает на прежнем volume.

## Подтверждённая причина и малая правка

В предыдущих трассах Planner заново оценивал уже начатую approved-процедуру и смешивал порядок в источнике с выполнением шагов клиентом. ProgressLedger сохранял показанные проверки, но терял подтверждение порядка исходного раздела.

В существующих `shown_units`/`eligible_units` теперь сохраняется `source_order`: SHA всего approved-файла и подпись текущей задачи, операции, объекта, цели, маршрута, модели, ограничений и explicit unknown. Это не клиентский факт и не статус выполнения. Повторное использование возможно только для незавершённой процедуры, присутствующей в текущих retrieved/applicable sections, при неизменном источнике и контексте. Planner всё равно заново проверяет применимость к текущим фактам; `applicability_confirmed=false` или иной mode не обходится. Модельные, SHA, safety и subject gates сохранены.

Выбор Planner сужается до активного раздела; исходные sections остаются у renderer для проверки связанных условий и предупреждений. При ревью промежуточной правки найден риск удаления этих связанных разделов при сужении всего списка. Это исправлено до запуска worker. Отдельный тест с изменённым связанным условием подтверждает `source_context_section_changed`. Второй тест проверяет SQLite reopen, продолжение при ложном order=false, отказ при applicability=false и отмену подтверждения при изменении SHA/операции.

## Фактические ответы

[order_memory_20261029_live.json](order_memory_20261029_live.json): **4 turns / 8 HTTP200**, без ошибок. Тот же трёхходовый Эвотор 7.3:

1. Бот выдаёт approved-шаг печати диагностического отчёта.
2. После «отчёт напечатал» выдаёт следующий блок EoU/интернет/параметры ОФД; не перескакивает на другую процедуру и не эскалирует преждевременно.
3. После явных результатов выдаёт: «Если базовые проверки не выявили причину, передайте диагностический отчёт в поддержку Эвотора». Не спрашивает результат повторно и не объявляет compound check выполненным: статус остаётся unknown.

Latency трёх реплик: **5446 / 4116 / 4271 ms**. aQsi scanner получил только approved-факт о совместимости (5163 ms); это **частичный ответ, не завершённая диагностика**. Начальный выбор новой процедуры по-прежнему может ошибаться: сохранение уже подтверждённого порядка не решает все случаи false order.

Этот успешный прогон был **до** поправки сохранения связанных sections. Финальный сохраняемый код прошёл локальный контроль, но его полный повтор [continuity_verified_20261029_live.json](continuity_verified_20261029_live.json) завершил только первую реплику; на второй Planner получил HTTP429 TPD. Поэтому не утверждаем, что финальный runtime полностью прошёл real E2E. Смена сервиса в этом последнем batch **не достигнута**; предыдущие успешные scope/reset/unknown-model результаты остаются baseline, не новым live-доказательством.

[order_memory_controls_20261029_live.json](order_memory_controls_20261029_live.json): Эвотор 6 повторно получил правильную approved-инструкцию (5667 ms); следующий БИФИТ остановил batch на Understanding HTTP400. Дополнительная diagnostic-попытка БИФИТ прошла без изменения Understanding, что не было принято за устранение ошибки.

## HTTP400: причина, отрицательный эксперимент и воспроизведение

[understanding_provider_repro.json](understanding_provider_repro.json) содержит **синтетический** запрос без ключей/headers, hash запроса и отклонённые ответы. В ограниченном трёхкратном воспроизведении один и тот же запрос дал два успеха и один HTTP400. Непустой `failed_generation` содержит поломанный второй элемент `entities` и незакрытый корневой объект. В последующем эксперименте один отклонённый output был пустым, второй снова сломан на втором entity. Это не потеря операции локальным validator: HTTP400 возникает до его вызова. Повреждённый output никогда не импортировался в state.

Проверен один ограниченный повтор только для provider code `json_validate_failed`, с прежним quota gate и полной валидацией нового ответа. **Live-результат отрицательный:** [order_retry_final_20261029_live.json](order_retry_final_20261029_live.json), два последовательных HTTP400, 8182 ms, полезного ответа нет. Retry **откачен**, его три временных теста удалены вместе с отвергнутой реализацией; локальный snapshot сохранён в `.local/rejected-understanding-retry/`. Запрос, schema и модель не заменялись при повторе.

Текущий запрос соответствует документированным обязательным полям и closed objects. [Groq Structured Outputs](https://console.groq.com/docs/structured-outputs) заявляет strict mode для GPT-OSS 20B; наблюдаемый отказ противоречит этой гарантии. Конкретный дефект внутри Groq не установлен. Гипотеза о grammar/complex-object schema требует отдельного контролируемого эксперимента; не объявлена доказанной. Модель и strict validation не ослаблены ради зелёного результата.

Последний HTTP429 явно сообщает **tokens per day**, limit 200000, Used 197003, Requested 4081, retry-after 469 s. Runtime diagnostic при этом маркирует dimension как `tpm`: это отдельная наблюдаемая неточность диагностики, не доказательство минутного ограничения. Квота не обходилась, дальнейшие запросы не выполнялись.

## Итоговые проверки и границы

- Финальный suite: **545 passed / 4 xfailed / 13 warnings**; `.local/live_recovery_pytest_continuity_final.txt`. От исходных 535 добавлено десять небольших проверок, не сотни новых сценариев.
- За это продолжение: **21 HTTP attempts / 13 turns**. Вместе с сохранённым baseline этапа: **125 HTTP / 80 turns**, **115×200, 6×400, 4×429**, известный usage **306263 tokens**. Ошибочные ответы не всегда возвращают usage; это не нулевой расход. Все попытки, включая неудачные и отвергнутый retry, включены в [метрики](live_metrics.json) и [неизменённые тексты ответов](answers.md).
- Новая runtime-правка сохранена только в `source_first_service.py` и `dialogue_state.py`; всего в исходной repair-работе изменены восемь runtime-файлов. Дополнен изолированный harness для диагностики отвергнутого JSON. `dialogue_understanding.py` возвращён к состоянию до retry-эксперимента.
- `.env`, модель, allowlist, approved KB и Qdrant index не менялись. Production SQLite не использовались для синтетических turns. Commit/push и Telegram send не выполнялись.

**Следующий конкретный шаг:** использовать сохранённый synthetic repro для ограниченного сравнения семантически эквивалентных форм nullable-object schema при том же strict contract и модели; оценивать не только отсутствие 400, но и сохранность exact-span facts. Затем повторить не завершившийся полный Telegram-equivalent memory/scope gate при доступной квоте. Не считать случайный успешный повтор ремонтом и не запускать worker до завершения gate.
