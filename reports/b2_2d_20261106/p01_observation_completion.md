# B2.2d / P0.1 — продолжение по наблюдению

Старт: локальный `main` на `2b720e5` с незакоммиченными изменениями предыдущего задания. Исходный факт-only ответ и его тесты сохранены; commit/push не выполнялся. Вопросы для LIVE зафиксированы до запуска в [основном manifest](p01_observation_live_manifest.json) и [дополнительном manifest](p01_observation_live_additional_manifest.json).

## Найденные причины и итерации

1. Understanding передавал точное наблюдение в DialogueState, но прежняя `_observation_explanation` требовала ранее показанный unit и буквальное пересечение слов. Первый fact-only ответ намеренно не показывал проверку, поэтому условие не выполнялось. Добавлен ограниченный маршрут с подтверждением актуального span, selected evidence, customer scope, SHA, indexed/local и проверкой смысловой связи моделью через допустимый ID. Неподтверждённое сопоставление не генерирует технических действий. После модельного вызова источник проверяется повторно.
2. [Первый настоящий вызов](p01_observation_live.json) остановился на Groq HTTP 400 `json_validate_failed`: отклонённый моделью ответ был синтаксически неполным. Его текст в состояние не использовался. Добавлен однократный ограниченный повтор только для этого типа HTTP 400; другие ошибки не переназначаются и отклонённый JSON не восстанавливается.
3. [Следующий LIVE](p01_observation_live_retry.json) обнаружил, что при `source_order_complete=true` первый вопрос всё ещё попадал в процедурную ветку и создавал check. Исправлено: ограниченный информационный маршрут определяется вопросом и проверенным фактом при любом значении полноты порядка, без глобального допуска процедуры.
4. [LIVE после этого](p01_observation_live_after_fix.json) прошёл исходные два хода; независимый второй ход скопировал смешанный раздел и создал check. Реальный Understanding не выделил `goal`; редуктор сохранил части вопроса как детали, и наиболее длинная деталь вытеснила наблюдение. Выбор ограничен точными spans первой повествовательной части сообщения; добавлен replay с сохранённым реальным Understanding.
5. [Следующий LIVE](p01_observation_live_final.json) снова прошёл исходный двухходовый сценарий, но на независимом втором ходе модель ошибочно пометила слово из названия компонента как модель оборудования; это дало ложный конфликт scope и новый task. Добавлено ограничение для одиночных общих предметов из существующего словаря `OBJECTS`, без отрицания подтверждённых номерных моделей. Сохранённый реальный Understanding воспроизводится offline. Первая версия ограничения пропускала склонение слова с трёхбуквенным корнем; исправлено и проверено отдельно.

Полный pytest до последнего исправления сущностей: **817 passed / 4 xfailed** ([лог](p01_observation_final_pytest.log)); это не результат текущего runtime. После исправления сущностей адресно **80 passed**; полный текущий pytest и последующий LIVE выполняются отдельно. P0.1 до окончательной оценки остаётся NO-GO. Frozen holdout, P0.2, B2.3 и ручной Telegram не запускались.

6. После исправления распознавания сущностей полный pytest — **822 passed / 4 xfailed** ([лог](p01_observation_scope_fix_pytest.log)). [Настоящая серия](p01_observation_live_scope_fix.json) завершила 10 ходов, 10/10 SQLite reopen: исходный и независимый диалоги, явное сообщение о результате и aQsi прошли по содержанию; будущая проверка не отмечена выполненной, но вместо ответа об обоснованности вывода бот запросил модель. Серия: 21 HTTP 200, ошибки/usage не смешивать с предыдущими запусками. Это частичный FAIL по качеству, а не общий GO.
7. Для последнего вопроса добавлен проверяемый fact-only повтор в рамках активной задачи: код и scope сверяются независимо, смысловая релевантность проверяется через ID локально подтверждённого evidence, а будущее действие не объявляется выполненным. Воспроизведён сохранённый Understanding, добавлен отрицательный контроль запроса опасного действия. Адресный профиль — **110 passed**, отдельный контроль — **2 passed**. Полный pytest на этой версии и повтор LIVE — следующий gate.

## Результат последнего gate

**P0.1 GO для проверенного ограниченного контракта; общий B2.2d и production остаются NO-GO.** Полный pytest текущей версии: **824 passed / 4 xfailed** за 229 с, [лог](p01_observation_continued_pytest.log). Оба бывших xfail исходной пары теперь обычные PASS. Четыре прежних xfail остаются: диагностический кандидат для другого кода, ответ на вопрос о месяце и два продолжения общих проверок Эвотора. Для другого кода отдельный тест конечного ответа проходит, но диагностический отбор кандидата остаётся открытым. Эти xfail не объявлены исправленными.

[Финальный Groq LIVE](p01_observation_live_continued_fix.json): `bot.handle_message`, настоящие Understanding и Planner, read-only Stage3, отдельная SQLite; пять двухходовых диалогов и **10/10 совпадений SQLite reopen**, все пять вторых ходов сохранили `task_id` и идентичный ProgressLedger. В четырёх диалогах Эвотора `checks` и `shown_units` пусты, `procedure_id` не создаётся; в aQsi прежний `asked` остался прежним без результата. Все 12 изолированных SQLite/checkpoint-файлов прошли `PRAGMA quick_check`. Подтверждённый usage финальной серии — **22 HTTP 200, 46 562 tokens**, ошибок провайдера нет.

- Исходная пара: по одному коду нельзя окончательно решить вопрос замены; на «неверные часы на кассе» бот процитировал наблюдение, объяснил возможное ложное впечатление о сроке и предложил специалиста.
- Независимая пара: «время отстаёт на несколько часов» связано с тем же проверенным фактом без смены задачи.
- Будущая проверка: бот не считает её выполненной и отвечает, что одного кода недостаточно для вывода о замене.
- Сообщённый результат: бот цитирует «Я проверил время на кассе: оно установлено неверно», объясняет факт и не создаёт `result_span` или `passed`.
- aQsi: первичная проверка дана по источнику; изменение USB передаётся специалисту, если стандартные проверки не помогли.

Факт в ответах Эвотора подтверждён `data/knowledge/evotor/fn/fn-234.md — Первое различение причины`, SHA `af72256e00ea74b476f596fb5426e49ea86b39b609c284b0deaf689cddc576ee`; units `ev-a9afd78fc69acceed457524a` и `ev-0a0b5a5c4602276ee633fd47`. Модельный судья выбирал только разрешённый ID; полные выходы, Planner, scope и состояние находятся в JSON. Хэши неизменённых manifest: `993fe6f61da0bc98be3d24d66847b8bd382686c9c6868c24acf83bc6857cd4a9`, `788bb53cb29f5a9f8c74920ee20c2da695a4b2596427ebd3beab32948dd3035f`.

Все шесть серий этого задания: **64 HTTP 200 / 139 140 подтверждённых tokens**, плюс один HTTP 400 без подтверждённого usage; 31/31 SQLite reopen. Неполные серии останавливались после выявленного сбоя и не выдаются за успешный gate. Рабочий Qdrant возвращён в исходное остановленное состояние; запросы к Stage3 шли только через read-only клиент. Approved KB не менялась.

Границы: отбор причинной пары поддерживает ограниченную структурную форму источника и не является универсальным извлечением произвольных фактов, условий и процедур; семантическая модель может отказать и не гарантирует переносимость за пределы проверенных случаев. Ручной Telegram, frozen holdout, остальные задачи B2.2d и доставка специалисту не проверены этим gate. Переход к P0.2 только после согласования; commit/push нет.
