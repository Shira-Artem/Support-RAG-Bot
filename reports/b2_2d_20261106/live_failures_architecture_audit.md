# B2.2d — архитектурный аудит сохранённых LIVE-ошибок

06.11.2026. Только локальный checkout `main`, HEAD `f743a6193156881b7c9bbcf7aa48c1402ba32af2` **с уже существующими незакоммиченными изменениями**. Аудит: чтение кода, approved-файлов и сохранённых JSON; без исполнения pipeline, новых Groq-вызовов, тестов, доступа к SQLite/Qdrant или production. Runtime, prompts, тесты и KB не изменялись. Главный план не редактировался по условию задания.

## 1. Краткий диагноз

Проблема системная, но оснований заменять hybrid Retrieval или строить новую агентную архитектуру нет. Смысл запроса теряется на нескольких границах: модельная классификация → reducer, операция документа → допустимый ответный фрагмент, выбранный раздел → фактический ответ. Один механизм не объясняет все ошибки, и не все отказы ложные: для N06/2 локальной approved-инструкции по сотруднику АТОЛ Онлайн не обнаружено. В u02 hybrid действительно находит нужную статью, но последующая проверка операций закрывает доступ даже к ограничению совместимости. В u01 прямой источник также найден и допущен, однако отрезан до Planner правилом выбора одного документа. В N07 определение уже доступно SourceFirst; короткое название «ФН» исчезает из признаков предмета, и служебная цитата выигрывает по общей лексике продукта. N03/2 и N04/2 объединяет приоритет незавершённой проверки над текущим сообщением, однако у N04 дополнительно не извлечено и не сохранено наблюдение о неверном времени. d10 и m01 показывают обратную сторону дословного копирования: оно сохраняет источник, но не обеспечивает релевантность каждой фразы и учёт известных фактов. Дефекты серьёзны для универсального помощника и сохраняют quality/production NO-GO; исправлять следует контракты существующих компонентов, сохраняя независимые safety, scope и SHA gates.

**Предел доказательства.** Основное evidence — [расширенный LIVE-отчёт](../b2_2d_20261105/expanded_live_report_20261106.md) и его первичные трассы. Сверка `source_hashes` в JSON с текущими локальными файлами показала: для исходных серий отличие runtime — только уже имеющаяся поправка `app/retrieval_pipeline.py`; для `N01_after` все сохранённые runtime SHA совпадают. Следовательно, исходные ответы нельзя называть новым прогоном текущего кандидата. Исторические успешные b01/h08 и N01_after — регрессионные опоры, а не свежая проверка всех ветвей. Состояние работающего worker и текущий Stage3 этим аудитом не устанавливались.

## 3. Общие архитектурные проблемы

**Категория и операция используются одновременно для поиска и разрешения действий.** Проверки нужны, но вопрос о возможности/ограничении не равен запросу выполнить процедуру. В u02 информационная реплика с `device/explain` идёт техническим путём (`app/ai_coordinator.py::coordinate`), а `query_operation_hints` читает контекст «подключаем» как другую операцию (`app/procedure_policy.py:81–106, 258–309`). В u01 safety-правило одного coherent документа одновременно становится необратимым relevance-выбором (`app/retrieval_pipeline.py:1233–1274`). N01 подтверждает отдельный конфликт повторной классификации: `_state_task_category` ставил settings раньше billing; локальная поправка на строках 573–577 уже проверена [N01_after](../b2_2d_20261105/expanded_live_20261106_N01_after.json). Это не доказывает, что все operation mismatches нужно ослабить.

**Relation, наблюдение и прогресс — разные измерения, сейчас связаны неполно.** Новый вопрос внутри той же задачи не обязан менять task_id. `coordinate` в основном проецирует состояние reducer и не управляет содержанием ответа. `_approved_check_units` принимает каждый numbered item без требования проверочного действия (`app/source_first_service.py:642–677`); `_reduce_progress` использует лексические outcome-предикаты (`app/dialogue_state.py:1565–1704`); fallback сохранения текста зависит от relation/type (`:1468–1501`). Поэтому N03 получает фиктивное обязательство отчитаться за факт, а N04 не получает record наблюдения. Финальный guard (`app/source_first_service.py:2599–2638, 2769–2863`) блокирует ответ, хотя сообщение доступно Planner. В исследованных случаях не доказано, что Coordinator сам неправильно удерживает task: для N03 продолжение уместно, N06/2 вообще сменил задачу.

**Grounding не проверяет достаточность ответа.** `claim_supported` проверяет поддержку утверждения источником и сразу принимает буквальное вхождение (`app/response_grounding.py:424–443`), не соответствие вопросу. N07 дополнительно проходит слабый conceptual gate (`app/source_first_service.py:352–476, 1796–1889`; `app/semantic_evidence_selector.py:115–132`). Exact-copy ветка по умолчанию копирует весь раздел и добавляет соседние ограничения по заголовку (`app/source_first_service.py:2553–2574, 3147–3200`). Это объясняет общий корень m01, d10, служебных добавлений N01/N02: подтверждённость смешана с релевантностью и полнотой. Существующий `_shown_section_limit` помогает h08, но его закрытая грамматика документов не является общим решением вопросов о USB или продаже.

**Один active_route недостаточен для двух сервисов в разных ролях.** В N06/1 АТОЛ Онлайн — контрагент/сервис, Диадок — интерфейс обмена. `DialogueManager.advance` считает несколько значений одного route-slot неоднозначностью (`app/dialogue_state.py:1392–1429`), `build_rag_query` прекращает работу при analysis_required (`app/rag_query.py:29–33`). Это ограничение представления, а не доказательство неспособности модели понять реплику. Вместе с предыдущими механизмами оно ограничивает использование естественного языка, но снятие проверок и свободная генерация не обоснованы: [master plan](../../docs/RAG_MASTER_PLAN.md) сохраняет отрицательные результаты Oracle/Model Benchmark.

## 5. Последовательность реализации и LIVE-проверок

1. После отдельного разрешения на реализацию зафиксировать локальный кандидат и критерии: текущая реплика не потеряна; question ≠ выполненная проверка; approved факт ≠ разрешённая процедура; каждый ответ содержит прямой ответный фрагмент и необходимые условия. Начать с двух P0-контрактов, затем applicability и роли сервисов; не добавлять списки исключений под сценарии.
2. Для каждого изменения сначала адресные offline-контроли и сохранённые трассы, затем подходящие регрессионные тесты. Сохранить [b01/h08](../b2_2d_20261105/fixes_live_20261105.json), отрицательные контроли из [отчёта исправлений](../b2_2d_20261105/b01_h08_fix_20261105.md) и [N01_after](../b2_2d_20261105/expanded_live_20261106_N01_after.json). b01 LIVE/2 был `explain`; ветка `check` доказана ранее offline, не объявлять её уже проверенной настоящим Groq.
3. Только по отдельному разрешению выполнить bounded `bot.handle_message → Groq Understanding → reducer → hybrid Stage3 → реальный Planner/selector → SourceFirst`, с отдельной SQLite на сценарий. Повторить дефектные ходы с необходимым первым ходом; добавить заранее зафиксированные независимые парафразы и отрицательные контроли затронутого механизма. b01/h08/N01 — адресные положительные регрессии при изменении общих контрактов, не основание повторять всю историческую серию. Сохранять candidate/rejection причины, доступный Planner контекст, выбранные IDs, exact spans, Ledger и reopen equality, usage/errors.
4. Принимать по содержанию ответа и состоянию: N03 без фиктивного выполнения; N04 с признанием неверного времени без выдуманного исправления; u01 с условием прежнего использования; u02 без обещания совместимости; N07 с определением; m01 без чужой темы; d10 с признанием известного и оставшимися условиями. Остановиться при safety-регрессии. Старые успешные JSON и pytest не заменяют новый E2E. Десять frozen holdout остаются закрыты до отдельного решения после стабильного кандидата.
