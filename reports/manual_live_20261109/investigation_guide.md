## Вопросы для раздельной проверки

### Исследование A — Python-гейты, SourceFirst, Planner и fallback

Проверить, на каких конкретных ходах сохранённые кандидат/состояние проходили или не проходили границы applicability, source scope, exact error code, selector/planner, Composer, grounding/relevance и fallback. Не предполагать заранее, что Python-фильтры чрезмерны; сопоставлять весь входной task snapshot, retrieved sections, raw model proposal (если записан), validator decision и Telegram answer.

### Исследование B — альтернативные механизмы

Независимо проверить Understanding, relation/topic transition, восстановление DialogueState, активную цель и уточнения, формирование RAG Query, hybrid retrieval/candidate order, prompts/evidence, маршрутизацию и квотные/provider сбои. Не предполагать заранее, что одна из этих стадий виновата; искать для каждого вывода положительные и отрицательные свидетельства.

Эти вопросы — планы проверки, а не выводы из текущей выгрузки.

## Изоляция дальнейшей работы

Создать две отдельные ветки или worktree, обе строго от code baseline `fce09b4`, например:

- `codex/investigation-a-python-gates`
- `codex/investigation-b-understanding-retrieval`

В каждом вести отдельный журнал экспериментов. Не переносить исправления между ветками до независимых результатов и согласования сравнения. Отчётный commit этого пакета содержит только документацию; его можно использовать для навигации, но базой кода остаётся `fce09b4`.

## Карточка хода для сравнения

Для каждого относящегося к гипотезе хода записать:

1. `Dxx-Tnn` и точный конечный текст.
2. Факт из записи и интерпретацию (в отдельных полях).
3. Какую стадию проверяешь и какие входные поля/решение это подтверждают.
4. Конкурирующее объяснение и данные, которые могли бы его опровергнуть.
5. Уровень уверенности: доказано / вероятно / неизвестно.
6. Что отсутствует (`not_recorded`) и какие read-only артефакты можно проверить дальше.

## Сверка выводов

После независимой разметки сравнить не только найденные причины, но и ходовые ID, процитированные поля, несогласия и пробелы. Не превращать совпадение двух гипотез в доказательство без trace evidence. Сохранять отрицательные результаты и менять рабочую гипотезу только после проверки конкурирующих объяснений.
