## Changes

- Common bounded connection recovery: at most three attempts, 1/2 s waits, **only HTTPX ConnectError/ConnectTimeout**, including explicit PTB exception chains. Those failures occur before an HTTP request is sent. Read/write timeouts, remote disconnects after sending, HTTP errors, invalid JSON and application failures do not enter this retry path. No completed LLM call is regenerated by connection recovery; existing Groq HTTP retry policy is unchanged.
- Native Telegram HTTPXRequest uses that recovery for delivery/poll requests. Read-only `getMe` startup has nine connection attempts: installed PTB initializes before its polling-bootstrap retry loop, and two release startups demonstrably exhausted the regular three-attempt budget. No extra LLM/sendMessage retries were added by this bootstrap exception. Typing is cosmetic: one short 1 s attempt, no retries; NetworkError/TimedOut cannot abort the question. No raw URL, credentials, identity or request body is logged by the retry helper.
- Undelivered assistant text and full Answer diagnostics are retained privately with `status=failed` and `delivery_status=failed`. They remain excluded from shown checks, reducer advancement and normal conversation history. `complete()` still runs only after successful delivery; no check is credited merely because generation finished.
- Hubris error responses carry the actual provider/model instead of the inherited Groq/OpenRouter label in the affected bot branches.
- Existing Selector cardinality is stated in its prompt; ID membership, approval, SHA, scope and procedure safety validation are unchanged. Its customer error message no longer exposes the word `evidence`.
- In the existing conversational profile, a **validated information / general / explain** turn without product-specific, procedural, legal/current-fact or risky context uses the existing model-only conceptual generator before retrieval. This is one runtime with the same reducer/memory, not a second worker/pipeline. The model explains naturally without pretending that it found a KB source. Technical instructions and named-product facts retain the approved-source path.
- Generic equipment classes with ordinary qualifiers are distinguished from confirmed model names; unknown names, numbered models, aQsi Online and Evotor 6 lite remain specific. Old persisted generic equipment claims are not treated as product identity by the conceptual eligibility check.
- The legacy fallback policy remains intact. The new ordinary-conversation route removes the 3-sentence/1000-character rejection and distinguishes descriptive verbs and invitations from imperative device instructions using the shared source-action vocabulary. Unsupported citations, normative/legal-status additions and unrequested imperative actions are removed sentence by sentence without inventing replacements or discarding the useful explanation. If none remains, it declines; a dangerous fiscal operation in the original output still rejects the whole response. This also caught an observed false legal-status claim in an intermediate model response. Eligibility, partial retention and output boundaries have positive and negative tests.
- Provider/model stay **Hubris / openai/gpt-oss-20b**. Real trials exposed basic conceptual errors at low effort; ordinary explanations use **medium effort and a 3072 completion-token budget**, without reducing quality to save tokens. Understanding and technical routes retain their configured settings. The general prompt names the Russian retail context and basic KKT/FN/OFD roles; it contains no customer-phrase dispatch or canned response.
- The existing full-pipeline LIVE harness forwards the optional completion budget when recording calls. One interim replay stopped on this harness signature mismatch; that negative result is preserved rather than reclassified as a provider failure.
