При дополнительной ручной проверке обнаружен семантический дубль b01 (загрузка по всем счетам) с B2.1. **До первого запуска b01** он исключён и заменён вопросом об отдельном списании возврата по эквайрингу. Новая [v2](baseline_frozen_v2.json), SHA-256 `2695395071ed440550abd28c0bb853058a3846c6804602d792585771e92b37cc`, содержит 24 случая / 30 ходов; каждый из шести блоков содержит четыре случая, многоходовых шесть. На момент поправки наблюдались только ответы k01; изменения не опирались на ответ заменяемого случая. Это явная поправка протокола после старта k01, а не утверждение о безупречной исходной заморозке. Вопросы k01 не менялись. Другие вопросы и ожидаемые минимумы после v2 не менять.

До LIVE для каждого covered-случая сохранены полный текст локальной approved-статьи, metadata и file SHA. Для неизвестных статусов и gap-контролей допустимые границы заданы отдельно. Рубрика A–H находится в frozen JSON; A не объединяется с B/C/D. Полезность ответа оценивается по вопросу, а не наличию найденной статьи. Неподтверждённые финансовые/фискальные действия и обход маркировки отмечаются отдельно.

## Реальный путь

Новый [harness](../../scripts/b2_2c_live_harness.py) наследует существующий transport-isolation harness. Настройки и фабрики возвращают реальные изолированные store/retriever; AsyncMock используется только вместо отправки Telegram-ответа и chat action. Understanding, reducer, Coordinator, SourceFirst, Planner/Composer и Stage3 не подменяются. Groq модель проверяется assert: `openai/gpt-oss-20b`. Режимы: SourceFirst/Coordinator включены, selector выключен; production worker не запускается. Вызовы реальны, failed provider responses не заменяются replay.

Qdrant Stage3 читается через wrapper, имеющий только collection_exists/get_collection/scroll/query_points. Индексация недоступна. Ожидается green/934. Тестовая SQLite и expert store лежат в уникальном `.local/telegram-equivalent-<output-stem>`; production SQLite не используется. Поддержка outbox выключена. `.env` только читается, настройки применяются в процессе.

Сохраняются raw/validated Understanding, request payload, HTTP public headers и usage, сообщения, TaskFrame, state до/после reopen и равенство, generation inputs/outputs, retrieval query/candidates/rejections/selected, scope/operation/Planner diagnostics при достижении стадии. `not reached` не трактуется как успешная проверка применимости.

## Ошибки стенда и квота

Первый старт с именем `baseline_live` остановился на ранее существовавшем каталоге исторического запуска, до Groq. Затем новый harness ошибочно вызвал property TaskFrame как функцию уже после ответа первого k01. Исправлен только harness; [ответ, Understanding и HTTP восстановлены из тестовой SQLite/trace](harness_initial_error_recovery.json). Этот запуск — диагностический повтор, не новый независимый случай.

[v2 live](b22c_baseline_v2_live.json) остановился на Understanding HTTP 429; Retry-After 115 с соблюдён до следующего процесса. [v3 live](b22c_baseline_v3_live.json) получил k01/1 HTTP 200 и k01/2 HTTP 429. Дневной лимит 200000, Used 199970, Requested 2836; Retry-After 1213 с от 17:32:38 UTC (20:32:38 МСК), не ранее 20:52:51 МСК. Ключ/организация/модель и completion allowance не менялись. Повтор или continuation допускается только после cooldown, с точной фиксацией checkpoint и без объявления незавершённых диалогов решёнными.

## Последовательность оставшейся работы

[12 зарезервированных новых случаев](holdout_reserved_NOT_RUN.json) пока **не AFTER-holdout**: подготовлены во время cooldown, требуют финальной проверки независимости и заморозки после исправлений. KB drafts не включены в approved retrieval и не могут улучшать текущий baseline задним числом.
