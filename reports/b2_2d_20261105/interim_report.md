# B2.2d — промежуточный отчёт перед паузой, 05.11.2026

Работа **приостановлена по просьбе владельца**. Этап IN_PROGRESS / LIVE INCOMPLETE, B2.3 и production NO-GO. Код и evidence сохранены без commit/push. Новый API-доступ предоставлялся владельцем через `.env`; агент файл не менял и значения ключей в отчёты не включал.

## Сколько реальных вызовов состоялось

Основной стенд: **44 попытки `bot.handle_message`, 39 технически завершённых ходов и 5 незавершённых из-за квот**. Groq: **66 HTTP, из них61×200 и5×429**. Дополнительно был один отдельный короткий успешный запрос проверки доступа,99tokens. Итого с ним67 HTTP /62×200 /5×429.

HTTP200 не означает полезный ответ: внутри удачно выполненного запроса возможны ложный отказ или нерелевантный факт. Ниже оценки фактических ответов, а не только соединения с API. Изолированный Telegram transport замокан; Understanding, reducer, Stage3, Planner и `bot.handle_message` настоящие.

## Что исправлено и что ещё не доказано

- Полный client span позволяет выбрать полный процедурный раздел даже при отсутствии optional `goal`. Одиночный соседний факт больше не достаточен для такого маршрута; h10 проверен LIVE.
- Предмет SIM/network и файлового импорта получает приоритет над coarse error/connect. Approved targets h01/h05 восстановлены без ослабления service/model/operation/SHA.
- Номер версии3.0.188 перестал ошибочно считаться пунктом инструкции; capability fact не обязан иметь форму определения. h07 LIVE A.
- Reducer сохраняет продукт при связанных explain/check/diagnose и access/credentials продолжениях. В b01/s01/m01 task/product пережили реальные SQLite reopen; новая независимая операция всё ещё создаёт новую задачу.
- Общая граница передачи секретов добавляет предупреждение, сохраняя техническую поддержку. Synthetic credential assignment удаляется **до Understanding и SQLite**; проверено через настоящий `bot.handle_message` в изолированном интеграционном тесте.
- Для m01 установлен ещё один механизм: procedure continuity скрывала ограничения того же source от Planner. Кандидат оставляет active procedure плюс её approved warnings; offline SourceFirst reproduction подтверждает предупреждение без повторного вопроса. **LIVE этого последнего m01 изменения ещё нет.**

Открыты h08, b01 operation metadata/выбор диагностики, общая полнота составных ответов, перенос правил обычного ЭДО/ЭПД и независимая проверка предупреждений в других сервисах. Отрицательные эксперименты и неудачные проверки не удалены; [хронологический технический отчёт](report.md), [единый реестр](../architecture_audit_20261101/b2_2b3_issue_registry_20261104.md).

## Токены: сколько стоит один вопрос

Фактический учёт [usage](token_usage.json): **144 564 подтверждённых токена** основного стенда, плюс99 проверки доступа = **144 663**. Usage пяти429 неизвестен, не объявляется нулём. У завершённых39 ходов расход137 260; среднее **3 519 токенов на один клиентский ход**, включая неудачные по полезности ответы. Это не среднее только успешных решений.

| Путь одного хода | Наблюдений | Среднее | Диапазон |
|---|---:|---:|---:|
| Только Understanding, далее локальная логика/цитата |20|2 301|1 925–3 225|
| Understanding + Planner |19|4 802|3 898–5 584|
| Все завершённые ходы |39|3 519|1 925–5 584|

Один многоходовый сценарий дороже одного сообщения: baseline в среднем4 236tokens/сценарий, выбранные регрессии5 777. По выполненным сериям: baseline76 241, primary regressions51 996, повторы/незавершённые попытки16 327 токенов. Это несколько прогонов одних и тех же вопросов для диагностики, не только18 клиентских обращений.

**Understanding потратил96 611tokens (66,8%)**, Planner47 953 (33,2%). Из общей суммы90 691 — входные токены,53 873 — выходные. Вход включает системные инструкции, schema, client/history/TaskFrame, approved sections и ledger. Выход включает служебный JSON, а не только короткий текст, который видит клиент. Отдельной LLM-генерации финального ответа в этих traces нет: после выбора утверждённый текст копируется локально. Надёжная разбивка основных вызовов на visible/reasoning в сохранённом HTTP usage отсутствует; нельзя считать recorded zero доказательством отсутствия reasoning.

По этой серии200 000tokens — ориентировочно **57 ходов среднего наблюдённого состава** либо **42 хода с двумя LLM-этапами**, если вся квота свободна, без внешнего расхода/повторов. Это арифметическая оценка, не гарантия ёмкости. Дешёвая цена модели не увеличивает лимит количества токенов. Лимит Groq200 000 — TPD организации, не бюджет этого чата и не лимит на каждый новый ключ; [официальные пояснения](https://console.groq.com/docs/rate-limits). Нельзя приписать все200 000 одной этой серии или одному аккаунту: доступ владелец обновлял, полной account usage history здесь нет.
