## Проверенные причины и ремонт внутри B1

1. **Promotion:** reducer повышал только `general/unknown`, но неполный `device/diagnose` без симптома удерживал старый intent после конкретного `receipt/diagnose`. Теперь более конкретный intent повышает такую задачу при сохранении task ID; уже конкретный device-симптом не переименовывается. Проверки: [test_b1_memory_integrity.py](../../tests/test_b1_memory_integrity.py).
2. **Модель и SQLite:** валидатор либо отвергал `Модель 7.3`, либо принимал `equipment=7.3`; затем persisted validator отвергал `Эвотор 7.3`, потому что цитата содержит только число. Теперь контекстный номер модели связывается только с единственным подтверждённым производителем текущей задачи либо тем же текущим сообщением. Тот же проверяемый контракт применяется при повторном чтении SQLite. В новом/пустом контексте голое число не становится equipment; отрицание модели не принимается. Факт по-прежнему хранит точную цитату пользователя и message ID.
3. **ProgressLedger:** старое сопоставление по любому слову блока давало ложный `passed` составной проверки; нейтральное «проверил» стирало известный `failed`. Теперь отдельные клиентские наблюдения с цитатами хранятся внутри существующего `TaskContext.checks`; составной блок остаётся `unknown`, пока не подтверждены его части. Нейтральное сообщение не стирает известный исход. Последнее явное противоположное значение актуализирует статус, а история противоречия сохраняется. Шаг только `asked` не считается выполненным. После live 02.11 добавлены общие маркеры совпадения параметров и нестабильной связи: цитата «они совпадают» ранее классифицировалась как `unknown`. Общий procedure unit больше не получает второй `failed` от той же цитаты, если её полностью объясняет более короткий конкретный check unit; если общий unit уже был показан, он остаётся `unknown` с ссылкой на частичный результат. Повтор точного live user event на сохранённом SQLite state дал только один `failed` по очереди; это offline replay после 429, не post-fix Groq E2E. Это тот же ProgressLedger, не параллельная память.
4. **Речевой шум:** автоматически сохранённый остаток фразы должен содержать содержательное слово; местоименные и дискурсивные фрагменты вроде «У меня» не попадают в `details` и query. Содержательное «Очередь растёт» сохраняется. Это критерий для произвольного остатка, не правило под одно слово.
5. **Provider failure:** ошибочный ответ Understanding и quota-deferred не открывают новое expected-уточнение. Invalid JSON и HTTP failure сохраняют только типизированную диагностику, без raw provider content. При semantic replay неудачный user turn не переинтерпретируется лексически. [HTTP 400/429 SQLite replay](../../tests/test_telegram_pilot_sqlite_replay.py) и [timeout/JSON tests](../../tests/test_dialogue_understanding.py) проверяют восстановление.

Три промежуточных отрицательных результата сохранены: baseline нарушил модель, promotion и ledger; первый повтор выявил голый numeric equipment; второй — несовпадение live и persisted validation. Ни один не объявлен исправленным только по локальному тесту. Последний contextual repair не получил post-fix Groq E2E из-за 429.

**Новые B1 причины и исправления:**

1. ProgressLedger распознавал лишь узкие формы «не уменьшается/не отправляется», поэтому естественное «не передались/осталась той же» было `unknown`. Добавлены общие отрицательные/положительные формы передачи, неизменной очереди и корректности параметров; отрицательный исход не стирается нейтральным «посмотрел». Независимый [регрессионный тест](../../tests/test_b1_memory_integrity.py) и второй реальный Эвотор batch подтверждают именно этот переход.
2. Groq валидно процитировал новый симптом, но семантически назначил `device`; прежний resolver не распознавал непоступление чеков **оператору** без явного «ОФД». Контракт `receipt + failure-to-reach operator` теперь повышает vague device до `receipt/diagnose`, не затрагивая банковские документы. Тест проверяет ошибочную raw LLM-метку и отрицательный соседний случай; второй живой batch уточнения подтвердил тот же task ID и `receipt` после SQLite.
3. Reducer безусловно заменял корневой `symptom` каждым новым симптомом того же task. Теперь первая жалоба остаётся якорем, а последующие клиентские симптомы сохраняются в `details` с цитатами. Frozen [production replay](stage_b1_production_replay.json) сохранил исходный симптом на 557→559 и gold selected на 557/559/561/565. После этой правки полный живой сценарий противоречий не завершён.
4. Применимость модельных шагов бралась только из явного текста unit, хотя документ уже имел подтверждённую model metadata. Более того, SourceFirst дважды строил units: `eligible_units` и `shown_units`; первый offline ремонт пометил только первый список, что выявил [SQLite replay](../../tests/test_telegram_pilot_sqlite_replay.py) и был исправлен. Оба списка теперь получают модель выбранного approved документа; смена модели выводит старые шаги из активных списков, сохраняя исторические checks. Сравнение модели нормализовано по регистру. Это проверено offline; **настоящий post-fix Groq ход смены модели отсутствует**.
