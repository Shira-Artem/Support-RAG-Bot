# B2.2b — неоднозначность подтверждённой модели

Дата: 04.11.2026. Git HEAD `70c0e2fcfb93f73982e2d8fafe498cbbb7f33735`. В начале уже существовали локальные изменения B2.2a.1, они сохранены и присутствуют в проверяемом runtime; это не чистый опубликованный snapshot и не независимая проверка B2.2a.1 на новом SHA. В [сценариях](b2_2b_cases_20261104.md) заранее зафиксированы вопросы, ожидаемые результаты и SHA статей; Stage3 green/934, approved status и индексный body hash пяти источников сверены до live. [Промежуточный trace](b2_2b_live_20261104.json), [финальный trace](b2_2b_live_final_20261104.json); шесть отдельных диалогов, в №5 два хода.

## Первопричина и изменение

В B2.1 raw Understanding дал equipment «Касса Эвотор 7.3» со span всей фразы. Validator принял его, затем `_extract_known_entities` независимо добавил вложенный точный span «Эвотор 7.3». Оба были подтверждены одной фразой и не противоречили друг другу. `DialogueManager` сохранил оба значения в TaskContext/TaskFrame; `task_entity` возвращает значение только при ровно одном элементе, поэтому SourceFirst/ProgressLedger считал модель неизвестной и спрашивал снова.

В `dialogue_understanding.py` добавлено удаление дубликатов только при распознанной паре **из существующего реестра производителя и полного числового обозначения модели**; ограниченный общий префикс типа «касса» не меняет identity. Сохраняется более короткий подтверждённый span; разные модели, производители и суффиксы не объединяются. Локальные факты не заменяются догадкой из базы или ответа модели. Явная смена модели и новое обращение по-прежнему обрабатываются reducer, старые проверки остаются. Реальное уточнение разных устройств не устраняется этой правкой.

Промежуточный live №3 выявил связанную ошибку: при двух буквальных упоминаниях `aQsi 5` validator сначала проверял уникальный длинный evidence quote, а затем повторно искал короткий model text по всему сообщению; Understanding был отклонён, хотя Groq HTTP 200. Сохранён первый trace, исправлен поиск **внутри уже проверенного уникального evidence span**. После этого финальная серия запускалась заново на одном коде. Поле локализованного transliteration fallback этим изменением не затрагивалось; все варианты написаний не доказаны.

| № | Сценарий | Оценка |

| 3 | aQsi 5 + внешний сканер | FAIL по полезности: повторные упоминания прошли валидацию; scanner сохранён вторым equipment, а релевантная approved статья отвергнута task mismatch |

| 6 | Общий вопрос об ОФД | PASS: релевантный approved факт с областью источника |

В №2 provider вернул только одну equipment entity; deterministic extraction не добавил второе отдельное значение, поэтому live **не доказывает срабатывание новой дедупликации на другой марке**; сравнение алиасов проверено offline. При этом реальная связка производителя и оператора проявила отдельный дефект: `assess_source_scope` получает `state.task_entities`, а legacy route facade для receipt с OFD route показывает только оператора и скрывает manufacturer/equipment активной задачи. Дальше source-first разрешает только attributed fact branch и не находит conceptual evidence. Прямое отсутствие manufacturer в facade следует из кода и `source_scope_gate`; переоценка гипотетического исправления не проводилась. Это не KB gap.

В №3 raw Understanding вернул два уникальных длинных evidence spans с одним `aQsi 5`, валидатор теперь отработал, но отдельно принял «внешний сканер» как ещё один equipment, потому `task_entity` снова не имеет единственного значения. Нельзя автоматически объединять кассу и сканер. Retrieval отклонил релевантный `aqsi_devices/peripherals/scanner.md` по `task_mismatch:peripheral_setup!=error_diagnosis`; затем scope gate заблокировал чужой источник. Это независимая ошибка маршрутизации и типизации, а не отсутствие общей approved диагностики. Неполнота конкретной модели сканера — отдельное частичное KB покрытие, добавлена в [общую gap matrix](../kb_quality_sprint_20261028/sprint3_gap_matrix.csv). Исправлять эти механизмы в данном этапе не начали.

В №5 первый неопределённый ввод завершился предложением специалиста до появления симптома; второй ход сохранил `task:9` и Эвотор 6, выбрал конкретную статью и предложил проверить действие обслуживания ОФД. Произвольная точная смена модели/другие производители и поддержка модельных суффиксов вне простого числового формата всецело live не подтверждены; offline контроли и тесты B1 проверили отдельные сценарии.

## Проверки и решение

Финал: 7 ходов в 6 изолированных диалогах, **10 HTTP 200 / 23 488 tokens**, все 7 SQLite reopen совпали. Полезных результатов по сценариям 3/6 (№1, 5 второй ход, 6); один обоснованный запрос модели (№4), **ложных повторных уточнений модели 0**, но это не доказывает отсутствие остальных ошибок модели — №3 получил два разных типа оборудования в одном slot. №2/3 — не полезные ответы, несмотря на наличие подходящего частичного evidence; №5 первый ход также преждевременно предложил специалиста при пока неописанной проблеме. Промежуточная серия до последней правки: 4 HTTP 200 / 8 974 tokens, 3 хода, третий — validation failure; суммарно **14 HTTP 200 / 32 462 tokens**, без 429/400. Настройки квот и runtime allowance не менялись. Все обращения синтетические, Telegram внешне не отправлялся. Groq/Stage3 настоящие, Qdrant client предупреждал об отличии версии сервера.

Профильные регрессии после финальной правки: **109 passed**; полный финальный `python -m pytest -q`: **684 passed, 4 xfailed, 14 warnings**, Python 3.14. Это не заменяет live quality gate. Статус B2.2b: **NO-GO как общий gate разнообразных полезных ответов**, исходная B2.1 модельная ошибка подтверждённо исправлена в границе этого live и сохранённой fixture. Общий B2 и production остаются NO-GO. Точные последующие действия — согласовать приоритет scope facade и peripheral task/типизации; B2.2c не начинался. Код B2.2a.1 сохранён локально, его результаты не объединены со статистикой B2.2b. Production worker/SQLite, approved KB, Qdrant contents, CRM, Smart Navigation и `.env` не менялись; commit/push не выполнялись.
