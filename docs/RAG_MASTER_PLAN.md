# Support-RAG-Bot — генеральный план

Дата актуализации: 2026-10-28. Это **единственная актуальная дорожная карта**. [PROJECT_STATE.md](PROJECT_STATE.md) хранит хронологию фактов и решений. [RAG_RECOVERY_PLAN.md](RAG_RECOVERY_PLAN.md), [RAG_VNEXT_PLAN.md](RAG_VNEXT_PLAN.md), [RAG_ROOT_CAUSE_AUDIT.md](RAG_ROOT_CAUSE_AUDIT.md) и отчёты экспериментов остаются профильными и историческими материалами. Статусы: `PLANNED`, `IN_PROGRESS`, `BLOCKED`, `DONE`, `REJECTED`. `DONE` означает выполненную задачу в указанной области, а не автоматическое разрешение на production.

## Продуктовая цель и сохраняемые компоненты

Универсальный AI-помощник технической поддержки по ОФД, ККТ, ФН, Эвотор, aQsi, 1С, банкам, маркировке и новым темам должен понимать живую речь, сохранять активную задачу и факты клиента, находить применимые проверенные знания, давать полезные технические шаги, задавать содержательные уточнения и вовремя передавать обращение специалисту. Цель измеряется решением обращения и долей подтверждённых действий, а не стилем ответа или одним retrieval rank.

Сохраняем Qdrant и существующую базу знаний; hybrid search BM25 + Dense + RRF; approved-статус и проверки применимости документов; хранение диалогов, диагностические трассы и обезличенные тестовые данные. Сохраняем результаты P0/P1/P2 и отрицательные выводы [Oracle RAG](../experiments/oracle_rag/report.md) и [Model Benchmark](../experiments/model_benchmark/report.md). Production-компоненты не меняются одним фактом утверждения этого плана.

## Подтверждённое к началу V1.1

- В Oracle-условиях правильные approved-документы были предоставлены заранее, но GPT-OSS 20B выдумывала интерфейсы, роли и операции; 0/5 обращений решены по строгой рубрике. Это не сбой retrieval на A–C.
- [Model Benchmark](../experiments/model_benchmark/report.md): 30 сохранённых ответов, 15 на 20B и 15 на 120B. Обе модели удерживали тему; 120B предложила опасную неподтверждённую процедуру ФН. Простая замена модели не решила проблему. LLM-first без независимой проверки каждого утверждения не допущен.
- [Причинный аудит](RAG_ROOT_CAUSE_AUDIT.md) и [журнал восстановления](RAG_RECOVERY_RESEARCH_LOG.md) показывают также отдельные ошибки retrieval, task state и post-processing. Предыдущий P0–P2 план не отменён. P0.5 E2E-сравнение не выполнено.

### Handoff integration — offline candidate

**Offline integration DONE only with fake transport; live/production remain NO-GO.** A final D2 contract review found that the `progress_ledger_next_approved_check` shortcut selected an unseen unit from an approved section without checking that unit's model scope. The earlier integration E2E had explicitly confirmed “Эвотор 5i”, so it did not exercise unknown-model behavior. The shortcut now requires generic source-derived model applicability to match reducer-confirmed equipment; unknown model asks once, unsupported model fails closed, and changing model creates a distinct scoped unit. The old broad missing-equipment gate remains. Real bot/SQLite reopen regressions cover unknown, supported `5i`, unsupported `X500`, and switch `5i → X500`. The read-only ProgressLedger provider returns check labels/status/client quotes only for the exact conversation/task/current-model snapshot; packet messages are scoped to that reducer task. Delivery requires `TELEGRAM_SPECIALIST_CHAT_ID` to match independent `HANDOFF_APPROVED_CHAT_ID`; duplicate confirm, explicit retry, missing/mismatched recipient, failure/restart, and receipt checks are covered. Targeted bot/handoff tests: **42 passed, 5 xfailed**. Full suite: **443 passed, 5 xfailed, 0 failed** in comparable Python 3.12 environment using the existing ignored fixture through a temporary junction and an isolated optional `langgraph` dependency directory. The fixture was not read or copied. Safety S2 passes; D2.3 strict xfail remains. Integration was fast-forward merged into `main` as `5a8f9929fced459a6dbbc13c386d2bd74b70b687`; the integration branch is published as `origin/codex/support-rag-handoff-integration`. Post-merge full suite on this exact SHA in the clean integration worktree: **443 passed, 5 xfailed, 0 failed**. In the primary checkout one repeat was blocked only by its ignored Python 3.14 `.local/vnext-deps` shadowing the Python 3.12 `ormsgpack`; the exact merged commit passed in the clean worktree. The integration implementation commit is ready to push to `origin/main` after this documentation update. No Telegram send, worker switch, or production write occurred. Live/production: NO-GO. See [integration report](../experiments/architecture_recovery_audit/p1_handoff_integration_20261026.md) and [MVP report](handoff_mvp.md).

## V1.3 — безопасная сборка ответа

- **Цель / статус:** собирать финальный ответ из проверенных утверждений, сохраняя полезные подтверждённые действия, одно нужное уточнение и обоснованную эскалацию при реальном knowledge gap; `PLANNED`.

- **Риски / остановка:** фрагментарный ответ, потеря условия или порядка действий, общие повторные отказы. Остановить при опасном финальном действии или систематической потере полезных approved инструкций.
- **Перед V1.4 согласовать:** протокол слепой ручной оценки и правило, когда уточнять, когда эскалировать.

## V3 — ограниченный Telegram-пилот

- **Цель / статус:** ограниченный ручной Source-first запуск в прежнем Telegram worker по прямой инструкции пользователя 2026-10-25. V1.2-B quality gate остаётся `FAILED`; это сбор реальных трасс, не допуск качества и не запуск V1.2-C.
- **Архитектурное решение:** переиспользуются прежние меню, `ConversationStore`, `DialogueState`, legacy `AnswerService`, callback специалиста, Groq GPT-OSS 20B, Qdrant Hybrid Search и существующий allowlist. Нового бота, токена, polling handler или хранилища нет. После разбора трёх первых обращений Source-first получает общий pre-retrieval gate незавершённой задачи; source metadata сравниваются через одинаковую нормализацию с локальным approved YAML; информационные вопросы могут выбрать не-процедурную секцию; vendor/model scope процедуры проверяется по фактам активной задачи до Planner и renderer. Секции остаются точными и SHA/status/heading checks не отключаются.
- **Конфигурация retrieval:** раньше worker использовал `knowledge_organized_stage2_20261022` из `.env`, тогда как V1.2-B использовал уже существующую `knowledge_stage3_retrieval_20261022`.
