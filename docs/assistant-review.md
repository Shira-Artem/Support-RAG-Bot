# Набор для проверки качества

`data/assistant_review_scenarios.jsonl` содержит 30 синтетических ситуаций, 46 сообщений. Есть отдельные вопросы и цепочки уточнений: права, кабинеты, чеки, ККТ, ФН, ОФД, маркировка, ЭДО и ТС ПиОТ. Ожидаемые ответы составлены по локальным карточкам и требуют подтверждения специалистом. Статус draft у исходной карточки не превращается в approved после успешного теста.

Явный запуск с настоящими Qdrant и Groq (расходует API):

```powershell
.\.venv\Scripts\python.exe scripts/run_assistant_review.py --batch имя-прогона
```

Команда проверяет существующую коллекцию, делает SQLite online backup обеих рабочих баз и последовательно вызывает тот же AnswerService, что и Telegram. Она проверяет текущую модель GPT-OSS 20B / medium и не меняет настройки. Никаких изменений Qdrant, обучения модели или сообщений в Telegram нет. Паузы ограничивают темп вызовов. При трёх последовательных ошибках API прогон останавливается; автоматических повторов нет. Ошибку API нельзя считать ошибкой содержания ответа.

Каждый ответ сразу сохраняется в `assistant_review_attempts` в экспертной SQLite, вместе с состоянием, поисковым запросом, контекстом, исходным и итоговым ответом, валидацией и расходом токенов. Префикс `assistant_review_` отделяет этот набор от человеческих оценок. Исходные карточки и код сохраняются как снимок/хеши. Диалоги прогона находятся в отдельной `.local/assistant-conversations-имя-прогона.sqlite3`, а не в истории клиентов.

Читаемый отчёт и полный JSONL обновляются после каждого ответа в `data/evaluations/assistant_review/имя-прогона/`. Остановка не удаляет уже полученные результаты. Повтор команды с тем же именем продолжит пропущенные задания; незавершённый на момент аварии ответ будет отмечен прерванным в отдельной истории. Записанные результаты не генерируются заново. Для сравнения исправленного кода используйте новое имя прогона.

Пересобрать отчёт без API:

```powershell
.\.venv\Scripts\python.exe scripts/run_assistant_review.py --batch имя-прогона --export
```

Оценки помощника импортируются явным `--reviews путь.jsonl`: поля `case_id`, `turn_index` (с нуля), `score` (1–10), `verdict` (`pass`, `partial`, `fail`, `technical_error`), `error_layer`, `comment`, `corrected_answer`. Они всегда имеют `reviewer_kind=assistant`, `human_approved=0`. Оценки специалистов собираются отдельно через `/expert`; порядок описан в `docs/expert-testing.md`.

Ни сохранённый ответ, ни высокая оценка сами по себе не обучают бота. Следующий шаг — специалист проверяет спорные случаи и эталоны, после чего исправляются источники/логика и повторяется контрольный прогон. Векторную базу нельзя пополнять непроверенными ответами модели.

После разбора в сценариях могут появиться `candidate_answer` и `candidate_status=needs_human_review`: это предложенные помощником ответы клиенту, а не подтверждённые эталоны. Экспорт `candidate_dialogues.jsonl` сохраняет их с контекстом всего синтетического диалога. Старый результат прогона и его первоначальные ожидания в SQLite остаются неизменными; исправленный вариант находится в оценке помощника. Для нового прогона с обновлёнными ожиданиями используйте новое имя.
