- **Retrieval — доказаны разные исходы:** в 2/3/4/5/6 retrieval был достигнут; scenario 2 не прошёл task-category; scenario 3 прошёл candidate gate и остановился на scope; scenario 4 — service mismatch; scenario 5 — operation mismatch; scenario 6 имел selected approved источник.
- **Applicability — доказана:** подтверждена для scope gate сценария 3 и неверно затипизированного service контекста сценария 4; корректный hard gate сценария 2 сохранил distinction между выпуском и доставкой чека.

## Не более трёх исправлений-кандидатов (без реализации на этом этапе)

1. **Первым: общий валидируемый контракт intent/operation и типизированных entities.** Канонизировать эквивалентные значения относительно семантической пары, сохранять independently confirmed exact-span facts при отказе другого поля, не превращать технический компонент в service и не преобразовывать explanation в search автоматически. Не принимать поля без поддержанного класса + доказательства. Риски: false accept и неверная safety ветка; отрицательные проверки — противоположный код ошибки, другой service, неподтверждённый/противоречивый alias, цитата вне текущего сообщения. Критерий: approved retrieval реально достигнут для сценариев 4/5/7 при сохранении hard gates, а не только поменялся fallback.
2. **Сделать reducer/Coordinator ожидания производными от текущей структурированной задачи и подтверждённых фактов.** Очищать/пересчитывать `expected=task/details` только когда новый exact-span goal/symptom закрывает соответствующее требование; сохранять topic change, contradiction, close/new-task semantics. Риски: приклеивание старой задачи к новой; отрицательные проверки — смена темы, противоречие модели, пустое продолжение, неизвестная модель, завершение. Критерий для сценария 7: единичный валидный запрос достигает retrieval кандидата Эвотор 7.3; если не хватает обязательного параметра — уточняется именно он.
3. **Сделать scope clarification task-specific и сфокусировать final evidence sentence.** Сохранять все текущие metadata/SHA/applicability gates, но отображать отсутствующий metadata slot на фактический параметр для данной категории; для ответов выбрать минимальное точное предложение из уже проверенной секции. Сценарии 2/6 должны остаться ограничены точными source claims. Риски: опасное упрощение предупреждений или скрытие предусловия; отрицательные проверки — сохранение условий/порядка процедур, отсутствие утверждения «FN — прямой фильтр», отсутствие вывода о доставке aQsi по статье о выпуске. Критерий: сценарий 3 задаёт вопрос о конфигурации 1С, сценарий 1 не добавляет нерелевантный календарный случай, каждое процедурное предупреждение остаётся видимым.

Сценарий 2 требует нового approved evidence/редакционного решения для доставки уже сформированного чека; это не следует «чинить» ослаблением retrieval. Quota telemetry требует сохранять `estimate_tokens`/limiter cause для каждого local defer; изменения cap или reasoning не предлагаются без парного offline качества.

## Решение и следующий шаг
