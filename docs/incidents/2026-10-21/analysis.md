# Support-RAG-Bot: диагностика 21.10.2026

Исправлены управление контекстом, привязка параметра к объекту поиска и допуск документов по операции. Telegram-процесс не перезапущен. Новое поведение проверено офлайн; качество новой генерации GPT-OSS в Telegram ещё не измерено.

## Доказательства и восстановление

В SQLite найдены обе conversation. Сообщения клиента имеют id 49, 51, 53, 55, 57, 59, 61, ответы — следующие id. Фактическое время: **15:29:10–15:30:45 МСК**, а не приблизительные 15:28–15:30 из запроса. В SQLite время хранится в UTC.

- [Исходные данные диагностики без сокращений](historical.json).
- [Состояния и запросы после исправления](replay.md), [машиночитаемый replay](replay.json).

Сырые `historical.json`, `historical.md`, `replay.json` остаются локальными и исключены из Git; соответствующие ссылки работают в рабочей папке после экспорта. Для запуска регрессии из чистого checkout включён минимальный обезличенный файл `tests/fixtures/telegram-2026-10-21.json`: семь сообщений и исходные ответы модели без идентификаторов сессий, API-вызовов и остальной диагностики. Он используется `scripts/replay_incident.py`.

Исторические данные отделены от нового прогона. Из семи ответов **шесть действительно вызвали `openai/gpt-oss-20b`**; id=60 не вызывал модель. Это прямо сохранено в `llm_call_attempted`. Для id=59 в офлайн-прогоне используется помеченная заглушка, для остальных — записанные исходные ответы. Это не семь новых ответов GPT-OSS.

В базе есть снимки после пользовательских сообщений. Отдельных снимков после каждого ответа нет: для состояния перед следующим сообщением нужно применить `scenario/clarification_slot` предыдущего ответа к полю `expected`. Экспорт сохраняет эти данные отдельно и явно описывает реконструкцию. Начальное пустое состояние выводится из начала новой conversation. Полный сериализованный HTTP prompt не сохранялся: достоверно доступен **точный RAG-контекст**, состояние и текст клиента; нельзя объявлять восстановленный system/user envelope перехваченным HTTP-запросом. Внутренние рассуждения модели не сохранены и не восстанавливались.

| Сообщение | Что произошло в сохранённой диагностике | Причина в коде до изменения |
|---|---|---|
| 49. Создание учётки aQsi | `access / unknown`; выбраны также регистрация аккаунта, поддержка, настройки, мониторинг | Словарь не распознал «завести», а `unknown` автоматически считался подходящей операцией. Статическая категория `account` слишком широка |

| 53. Смотреть кассы и отчёты | Цель и запрет сохранены, но операция всё ещё `unknown`; ремонт оставил почти только навигацию | Неправильная операция дала лишние документы; восстановление не имело семейства текущей процедуры |
| 55. АТОЛ Онлайн | Сущность заменена правильно, но запрос содержит старый текст с **aQsi Online**; допущены активация ФН и замена Казначея | При `unknown` использовался исходный текст старой задачи. | 57. Список касс Платформы ОФД | `device / check`; ОФД сохранён, но категории задачи не было; среди допущенных — подключение, регистрация, ФН и поиск чеков | Для просмотра касс не было самостоятельного соответствия операции; отсутствие категории превращалось в широкий допуск |
| 59. Найти чек за месяц | `receipt / search`, переход `new_task`, `entities={}`; повторный вопрос об ОФД, LLM не вызван | `DialogueState(...)` при новой задаче сбрасывал **все** сущности. Исключение было только для сжатия слишком длинного запроса |
| 61. Найти его по номеру ФН | `fiscal_drive / search / ФН`, ещё одна новая задача; запрос `поиск ФН` | Статический порядок OBJECTS выбирал ФН без различения объекта поиска и аргумента; ссылка «его» не связывала объект с чеком |

В id=50 и 52 поля фамилии, пароля и проверка входом сохранились в конечных ответах. Механизм ремонта при `operation=unknown` принимал все локально не запрещённые предложения: ветка восстановления процедуры запускалась только при известном семействе операции. В id=56 он восстановил **фискальный** ответ из допущенных фискальных источников. Это не объяснение «модель просто галлюцинирует»: до генерации и после неё были конкретные ошибки управления и отбора.

Есть и дефект диагностики: прежнее `selected=True` обозначало все прошедшие фильтры документы, даже если лимит 5 документов не позволял включить их в контекст. Теперь выбранными помечаются документы, допущенные к расширению; фактически отправленный текст по-прежнему нужно проверять по `context` с учётом лимита символов.

## Что изменено

`DialogueState.entities` теперь хранит устойчивые факты **сессии**. Новая задача очищает требования, ошибку, параметры, ожидаемый вопрос и ссылку на объект, сохраняя сервис, ОФД и оборудование. Явное новое значение заменяет соответствующий слот. Смена производителя снимает устаревшую модель оборудования.

`routing_slot` связывает текущую задачу с активным кабинетом. `task_entities` — представление фактов для запроса и prompt: сведения об оборудовании остаются в сессии, но не становятся фильтром статей о поиске чека в ОФД. Это важно и для существующего Retriever: упоминание бренда в запросе включает его фильтр по брендам. Общее определение понятия не сужается до прежнего сервиса, если новый вопрос его не назвал.

Явное изменение операции над тем же объектом обновляет её даже в предложении с «мне нужно». Требования к возможностям сотрудника сохраняются как требования, а не новая задача о кассах. Добавлен один общеупотребительный глагол создания в декларативный словарь; исправление не сводится к этому дополнению.

В поисковых запросах анализируется отношение **объект → параметр**: прямой объект до параметра, ссылка на прежний объект при отсутствии нового прямого объекта, отдельные параметры с цитатами и `object_reference`. Это общий механизм для поисковых аргументов и коротких уточнений, без regex под семь предложений. «Найти чек по номеру ФН» и «найти его по номеру ФН» сохраняют чек; явное «заменить ФН» начинает другую задачу. Новый период заменяет прежний период.

Поиск теперь отдельно сопоставляет просмотр списка касс. Неизвестная операция не доказывает соответствие документа. Для изменения прав нужна подтверждённая операция изменения существующего пользователя, поэтому случайные слова про полномочия в инструкции ФНС не дают контекст для доступа к кабинету АТОЛ Онлайн. Мониторинг/смена ФН не проходят категорию поиска чека.

Ремонт ответа сохраняет извлечённые действия текущей процедуры; для access/credentials консервативное восстановление применяется и при неизвестном семействе, чтобы этот случай не возвращал непроверенные соседние шаги. Для параметра поиска, которого нет в тексте контекста, ответ прямо обозначает **неподтверждённость по найденной инструкции** и даёт подтверждённые поля. Не делается вывода о невозможности функции. Проверка лексического упоминания — только отрицательный сигнал полноты; наличие слова само по себе не считается доказательством фильтра.

Снимки старых сообщений не переписывались и повторно не классифицировались. Новые поля аддитивны, старые schema=1 читаются с пустыми значениями по умолчанию. Исправление не чинит задним числом уже потерянные факты старого снимка: повторение диалогов следует начать с новой conversation после отдельно разрешённого запуска обновлённого процесса.

## Ложные срабатывания и пределы доказательства

- Отказ валидатора принять сохранение пользователя объясняется неполнотой локальной карточки: официальный источник этот шаг содержит. Это не доказанная выдумка модели. Точное неверное название кнопки и придуманная матрица ролей — другой случай.
- Восстановление процедуры по буквальным исходным предложениям — сознательная консервативная политика. Изменённая формулировка может быть правильным пересказом; `procedural_details_not_grounded` не означает доказанную галлюцинацию каждого удалённого предложения.
- Нельзя доказать отсутствие функции создания ролей или фильтра по ФН по отсутствию текста страницы. Не подтверждены также фактические полномочия пользователя, наличие нужной роли и актуальный вид закрытого кабинета.
- Офлайн-прогон не воспроизводит dense ranking рабочей коллекции, задержку Groq или новое поведение модели. Он проверяет реальные тексты карточек, весь локальный набор кандидатов, reducer, query builder, штатные фильтры, расширение и ремонт записанных ответов.
- Семантика сложных сравнений, отрицаний и нескольких одновременно активных объектов остаётся ограничением лексического анализатора. Неподтверждённые отношения должны приводить к уточнению, а не догадке о новой задаче.

## Небольшой структурированный анализ для неоднозначностей

Рассмотрен следующий этап: один ограниченный LLM-анализ только при `analysis_required`, неизвестной операции конкретной задачи или конфликте связей. Не включён автоматически: это дополнительная стоимость, задержка и отдельный критерий качества. Для семи сообщений дополнительные вызовы не нужны.

Вход: текущая реплика, компактная задача и только пользовательские факты. Выход: `relation` (новая задача / изменение операции / параметр / требования / смена сущности / неуверенность), допустимые intent/operation, `object_ref` на существующий объект, entity/parameter patches. Каждый patch обязан иметь `message_id/start/end/quote`. Цитата проверяется точным сравнением подстроки, enum — белым списком, ссылка — существующим id, значение сервиса — допустимым названием из процитированного текста. Цитата «его» подтверждает ссылку, но не новое название сервиса. Низкая уверенность или несколько допустимых объектов → один короткий вопрос.

Сеть должна работать **до** SQLite-транзакции; при применении проверяется revision, чтобы поздний результат не менял уже обновлённую задачу. Контракт `MessageAnalyzer/Observation` и проверка цитат уже существуют. Синхронный анализатор внутри `ConversationStore.begin()` нельзя просто заменить сетевым вызовом: он удержит write lock. Нужны подготовка наблюдения вне транзакции и атомарное применение с проверкой ревизии. Эксперимент следует оценивать на этих же реальных сообщениях и небольшом наборе реальных неоднозначностей, включая неверные цитаты; не включать по факту прохождения словарных тестов.

## Проверка и сохранность

Добавлены **три** теста: один на полную семёрку с реальными карточками и записанными исходными ответами; один на связь поискового аргумента и явную смену операции; один на SQLite round-trip новых полей и сохранность оборудования. Прежние проверки, требовавшие стирать сервис при новой задаче, обновлены под требование сохранения контекста; проверка общего определения без постороннего сервиса сохранена.

Результат: **107 passed** (`.venv/Scripts/python.exe -m pytest -q`). Прогон использует подменённый генератор, внешних платных вызовов нет. Полный replay повторяется командой `.venv/Scripts/python.exe scripts/replay_incident.py`, исторический экспорт — `scripts/export_incident.py` (SQLite открывается с `mode=ro`).

Контрольные SHA-256 SQLite и экспертных данных записаны в `historical.json` и сверены после работы. Знания, экспертные оценки и существующие данные не удалялись. Qdrant не открывался и не переиндексировался. Не выполнялись commit/push или перезапуск Telegram. Для проверки в Telegram потребуется отдельно разрешённый запуск обновлённого процесса; действующий процесс продолжает использовать загруженный ранее код.
