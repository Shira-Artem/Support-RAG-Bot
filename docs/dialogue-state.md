# Структурированное состояние обращения

Этот этап меняет управление диалогом и подготовку запроса, не индекс и не модель.

## Путь сообщения

1. `ConversationStore.begin()` в одной SQLite-транзакции записывает сообщение клиента,
   применяет `DialogueManager.advance()` и сохраняет снимок. Старый аргумент
   `continuing` принимается для совместимости, но не управляет состоянием.
2. Telegram получает `dialogue_state()` и передаёт готовое состояние в
   `AnswerService.answer(..., state=...)`. Повторного разбора текущего сообщения нет.
3. `build_rag_query()` формирует самостоятельную задачу из типизированных полей.
   Он не склеивает переписку и не отрезает часть условия для соблюдения лимита 500.
4. Ответ сохраняется как раньше. `complete()` обновляет ожидаемое уточнение,
   но не превращает утверждения бота в клиентские факты.

CLI использует тот же manager в памяти. Изолированные экспертные вопросы не
получают состояние чужого обращения. Прежний `history=` поддерживается отдельным
адаптером для stateless-вызовов; Telegram и CLI им не пользуются.

## Схема

`DialogueState`: версия схемы, ревизия, ID задачи, ID первого сообщения темы,
intent, operation, объект, entities, цели, ограничения, дополнительные сведения,
код ошибки, ожидаемое уточнение, переход и признак необходимости анализа.

Сущности разделены на `service`, `manufacturer`, `equipment`, `ofd`, `software`.
Два оператора ОФД в одном сообщении не сводятся к первому совпадению; разные виды
сущностей могут присутствовать одновременно. `routing_service` — только проекция
для существующего интерфейса retrieval. Она не заменяет сущности в состоянии.

Каждый `Fact` содержит значение и происхождение: `message_id`, точную цитату,
начальную и конечную позиции в сообщении клиента. Intent/operation имеют отдельное
основание `operation_evidence`. Должность не преобразуется в роль продукта.
Название роли из документации должен подтвердить последующий этап RAG.

Переходы: `new_task`, `continue_task`, `clarification`, `refine_requirements`,
`change_service`, `change_parameter`. Изменение сервиса сохраняет задачу и требования;
новая независимая задача очищает прежние цели и параметры, сохраняя сущности сессии и историю.

`routing_slot` связывает задачу с активным кабинетом, `task_entities` выбирает факты
для запроса и prompt. Смена оборудования не подменяет кабинет текущего поиска чека.
`parameters` и `object_reference` сохраняют аргументы поиска и ссылку на прежний
объект с цитатами пользователя. Просмотр списка касс имеет операцию `list`.
Новые поля аддитивны для schema=1; уже сохранённые старые снимки не переписываются.

[отчёт](incidents/2026-10-21/analysis.md), [replay](incidents/2026-10-21/replay.md).

## SQLite и совместимость

Добавляются только таблицы:

- `dialogue_states`: текущий JSON-снимок и курсор последнего обработанного сообщения;
- `dialogue_turns`: снимок состояния после каждого пользовательского сообщения.

Существующие таблицы, история, ID сообщений, экспертная база и старые диагностические
JSON не переписываются. При первом чтении старого диалога выполняется однократное
восстановление из сообщений клиента и метаданных ожидаемых вопросов. Старым флагам
continuation не доверяем. После этого читаются только события за курсором.

Запись сообщения и снимка защищена одной `BEGIN IMMEDIATE`-транзакцией. Незавершённый
ответ останавливает курсор до `complete()`/`recover_pending()`. Повторный `complete()`
не перезаписывает результат. Версия снимка, которую код не понимает, вызывает ошибку,
а не очистку данных. Миграция запускается при открытии диалога обновлённым приложением;
рабочий бот в рамках разработки не перезапускается.

## Детерминированный анализ и границы

`LexicalAnalyzer` — ограниченный адаптер: словарь сущностей, объектов, операций и
дискурсивных признаков, затем типизированное наблюдение. Решения о переходе принимает
отдельный reducer. Это не универсальный семантический анализатор русского языка.
Местоимения и короткие ответы используются в контексте активной задачи/ожидаемого поля,
а не как самостоятельное доказательство прав или названия продукта.

Неоднозначное отношение сообщения к задаче и конкурирующие сущности одного вида
помечаются `analysis_required`. Поиск и генерация тогда не запускаются: бот уточняет
задачу. Если запрос не помещается в лимит retrieval, запрашивается краткое изложение
всех обязательных требований; отдельные ограничения не отрезаются молча.

Для следующего этапа есть `MessageAnalyzer` → `Observation` и внедрение manager в
`ConversationStore`. Будущий структурированный LLM-анализ должен использовать этот
контракт, вернуть проверяемые цитаты текущего клиентского сообщения и явно обозначить
неуверенность. Reducer проверяет происхождение фактов. В текущей реализации такого
API-вызова нет. Не следует расширять словарь до бесконечного списка исключений:
сложные отрицания, коррекции требований, неизвестные продукты и новые семейства задач
требуют отдельно измеренного семантического анализа.

Будущий сетевой анализ нужно выполнять до SQLite-транзакции и проверять ревизию
перед применением подготовленного наблюдения. Нельзя внедрять сетевой вызов прямо
в синхронный анализатор, используемый внутри `begin()`: он удерживал бы блокировку БД.

`clarification_slot` может возвращаться генератором в том же JSON-ответе, только при
`scenario=clarify`. Допустимые значения проверяются; старые ответы без поля используют
детерминированные причины или `details`. Вопрос бота сохраняется отдельно от фактов.
Настройки провайдера, модели, температуры, reasoning и лимитов не меняются.

## Проверка без сети

`python -m scripts.trace_dialogue_state` выводит состояние и запрос для пяти сообщений
из аудита. `--full` добавляет происхождение всех фактов, `--input file.json` принимает
другую последовательность. Скрипт не открывает SQLite и не вызывает RAG/LLM.

`tests/test_dialogue_state.py` проверяет точную цепочку и перефразирования, переходы,
сущности, сохранение/миграцию, ожидаемые уточнения, происхождение фактов, предел запроса,
неизвестную версию снимка, восстановление pending и отсутствие повторной классификации.
Тесты AnswerService подменяют генерацию и retrieval. Качество ранжирования и фактические
знания модели эти тесты не измеряют.

## Граница первоначального этапа (до исправления 21.10.2026)

Не изменены retrieval/RRF, пороги, расширение статьи, категории карточек, чанкинг,
embedding, статусы знаний, правила фактической валидации и полнота документации.
В частности, прежние ограничения поиска по числам/брендам должны быть согласованы
с разделёнными сущностями; структурированное состояние само по себе их не исправляет.

Последующее исправление управления задачами, выбором знания и ответа описано в
отчёте инцидента выше. Индекс, embedding и статусы знаний по-прежнему не изменялись.
