# Support-RAG-Bot — RAG vNext: план спасения качества

**Статус:** рабочий план для Codex; реализация не считается завершённой до подтверждённых результатов.
**Дата фиксации:** 23 октября 2026 г.
**Приоритет:** ответы, которые реально помогают клиенту, при сохранении безопасности.
**Репозиторий:** `Shira-Artem/Support-RAG-Bot`.
**Размещение в репозитории:** `docs/RAG_VNEXT_PLAN.md`.

> Этот план — ориентир для следующих шагов, **а не новая немедленная задача**. Первый промпт на изолированный CLI-прототип RAG vNext уже запущен пользователем. Не прерывать его, не запускать повторно и не делать второй прототип параллельно. После его завершения сверить фактический результат с этим планом, зафиксировать расхождения и перейти только к следующему обоснованному шагу.

## 0. Почему меняем подход

По сообщённому ручному прогону 23.10.2026 ни одно из 5 проблемных многошаговых обращений не было полноценно решено. Предполагаемые места отказа: преждевременные `message_ambiguous` / `service_not_confirmed` / `no_source_evidence` / `applicability_context_missing` / `no_task_matched_candidates`, некорректные переходы состояния и отбор доказательств. Это **гипотезы**, а не доказательство, что LangGraph или другая LLM сами по себе исправят систему.

Прежние `pytest passed` и retrieval benchmark не являются метрикой успешного решения обращения. Старые Telegram-логи также нельзя автоматически считать тестом точного P0/P1 runtime из-за ранее обнаруженного расхождения хешей запущенного worker и ожидаемого кода.

## 1. Цель, границы и принципы

**Цель:** проверить на идентичных сценариях, что небольшой альтернативный путь даёт более полезные, подтверждённые ответы, не теряет контекст и не придумывает опасные инструкции.

**Принципы:**
- Развивать **параллельный** минимальный CLI RAG vNext; текущий Telegram и production pipeline не переписывать до решения по пилоту.
- В первой версии: `LangGraph` для минимального сценария и памяти, существующие Groq `openai/gpt-oss-20b`, Qdrant + BM25 и доступные корпуса документов. Не добавлять одновременно DSPy, LlamaIndex, reranker, Ragas.
- Начинать с исходного вопроса и последних реплик, а не с преждевременного жёсткого `intent/operation` отказа. LLM может выбрать поиск или **одно конкретное уточнение**; после ответа помнить уточнённые факты, но не превращать догадки модели в факты клиента.
- Поиск и сопоставление кандидатов делать шире, чем старые ранние task gates, **но** после поиска не допускать явные несовпадения сервиса, производителя, модели, операции или неподтверждённые процедурные шаги.
- Сохранять grounding и safety: запрет опасных фискальных процедур без достаточного доказательства; не выдумывать UI, роли, кнопки, правовые правила и технические действия.
- При недостатке знаний — не универсальный циклический отказ, а конкретное недостающее поле, безопасная частичная помощь или передача специалисту. Не считать «уточнение» полноценным решением.
- Приоритет решений задаётся измеренными результатами, а не популярностью фреймворка.

## 2. Жёсткие ограничения безопасности эксперимента

1. **Не изменять** production SQLite, Qdrant-коллекции/points/индексы, `.env`, секреты, текущий Telegram worker, рабочие пользовательские разговоры.
2. Read-only доступ к источникам. Вынести прототип, трассы, тестовые checkpoints и конфигурацию в отдельную область; не смешивать их с production данными. Не обращаться к реальным приватным сообщениям без необходимости; использовать обезличенные тестовые реплики.
3. **Без commit/push** до явного разрешения пользователя.
4. **Не менять** старый `DialogueState`, P1 safety boundaries или продовую маршрутизацию в рамках этапа прототипа.
5. Любые вызовы Groq — только в пределах разрешённых тестовых сценариев, с фиксируемым числом вызовов/токенов и обработкой ошибок/таймаутов. Не запускать массовые автоматические повторы.
6. Перед тестом записывать git SHA, hash исходных файлов, активную коллекцию Qdrant, статус документов, настройки модели и факт demo/approved; **не предполагать** их текущие значения по старому отчёту.
7. В рабочем поиске `approved` обязателен. Если для тестов доступны только `draft`, использовать явно обозначенный изолированный **research/demo** режим, сравнивать обе версии на одном и том же допустимом наборе и **не выдавать** draft-ответ за готовый к production.

## 3. План по этапам и результатам

### Этап A — текущий запущенный шаг: минимальный CLI vNext

**Что делаем:**
- Минимальная LangGraph-схема: `conversation/messages → understand_or_clarify → hybrid_search → applicability/evidence → generate → grounding/safety → answer`.
- Отдельный CLI для многоходовых тестов; отдельное состояние/память, изолированные диагностические артефакты.
- Существующий Qdrant + BM25 **read-only**; без новой индексации и без reranker в первой версии.
- Для каждого хода — вопрос, интерпретация задачи, сохранённые ограничения, поисковый запрос, найденные и отсеянные документы с причинами, был ли вызов LLM, ответ, тип исхода (`answer/clarify/partial/escalate/error`), grounding и время.

**Приёмка:** CLI работает изолированно, не пишет в production, способен продолжить тестовый разговор, есть воспроизводимые трассы и инструкция запуска. Если API/API-ключ недоступен — это blocker, а не «успешный ответ».

### Этап B — парное испытание старого пути и vNext

**Набор:** 5 многошаговых проблемных сценариев + 2 позитивных с заранее проверенными подходящими документами:
1. «Закончился / истёк ОФД» и уточнения про оплаченный период.
2. 1С / DirectBank: перестали загружаться банковские выписки; затем уточнён сервис.
3. Неопределённое изменение ФН: корректное безопасное уточнение вместо перерегистрации.
4. Вопрос о подключённом ОФД → новая задача: сотрудник с правом только просмотра.
5. Срок договора с Платформой ОФД после уточнения сервиса.
6–7. Позитивные сценарии с содержательно проверенными и разрешёнными источниками (зафиксировать document_id и применимость до запуска).

**Сравнение:** одинаковая последовательность сообщений, одинаковый корпус и статус документов, насколько возможно одинаковые настройки Groq и явное разделение разных runtime-снимков. Если точный старый runtime недоступен, указать это и честно сравнивать с воспроизводимым pinned baseline, а старые Telegram-ответы оставить историческим наблюдением.

**В протокол для каждого хода:**
- Ожидаемое полезное поведение и критерии, написанные **до** просмотра вывода vNext.
- Реальный текст ответа каждой версии; не только агрегаты.
- Подтверждённые/неподтверждённые утверждения и опасные действия.
- Сохранность исходной задачи, сервиса, операции, ограничений; смена темы и количество повторных уточнений.
- Документы, их `status`, релевантность, применимость, evidence coverage, причины отказов.
- Количество вызовов Groq, задержка и расход токенов (если доступны).

### Этап C — решение о направлении

**Целевые критерии пилота** (гипотеза/ориентир, не уже достигнутые цифры):
- Полезное **решение** не менее 4/5 исходных проблемных случаев **когда применимые доказательства действительно доступны**. Иначе честно классифицировать как gap базы знаний, не завышая оценку.
- Оба позитивных контрольных обращения должны получить корректную помощь: 2/2.
- **0** опасных неподтверждённых действий и **0** выдуманных специализированных процедур.
- **0** подтверждённых случаев потери исходной задачи после простого уточнения; без циклов повторных вопросов.
- Внятное улучшение против pinned baseline по покомпонентному разбору. Уточнение, отказ или эскалация сами по себе **не равны решённому обращению**.

**Развилка:**
- Понимание и ответы реально улучшились, safety не хуже → расширить отложенную тестовую выборку, затем изолированный Telegram-пилот.
- Понимание хорошее, документы плохие → отдельно сравнить поиск с готовым multilingual CrossEncoder reranker, **не внедрять сразу**.
- Документы хорошие, ответ плохой → работать над промптом/генерацией/grounding по трассам.
- Нет применимого approved evidence → экспертная ревизия и пополнение базы; не решать галлюцинациями.
- Опасные или неподтверждённые инструкции → **STOP**: не выпускать в Telegram/production, расследовать.
- Нет заметного улучшения → не развивать vNext по инерции; отчёт о точном месте отказа и предложение альтернативы.

### Этап D — после успешного пилота

1. Сделать 50–100 **новых** разговорных тестовых реплик от двух тестировщиков, с заранее размеченным ожидаемым поведением (включая перефразирования, смену темы, неопределённые запросы). Часть выборки держать отложенной, не использовать для подгонки.
2. Расширить сравнение: доля решённых кейсов, безопасность, источники, стоимость, p50/p95 задержка и эскалации.
3. Запустить отдельный Telegram-пилот только после разрешения, с отдельными данными/участниками и возможностью быстрого отката.
4. Принимать архитектурное решение об интеграции **только** после ручной проверки и повторяемого регрессионного набора. Перенос в production — отдельная согласованная задача.

## 4. Короткая таблица решений

| Наблюдение | Действие |
|---|---|
| vNext лучше отвечает по применимым источникам и не рискует | Продолжить расширенные тесты, затем отдельный Telegram-пилот |
| Понимает вопрос, но retrieval выбирает не то | Диагностика кандидатов; затем A/B готового reranker |
| Retrieval хороший, но генерация выдумывает или отказывает | Улучшать генерацию/grounding, не маскировать проблему |
| Источников недостаточно | Экспертный аудит и обогащение approved знаний |
| Повторные уточнения и потеря темы | Править память и вопрос-контекст, проверять многоходовые тесты |
| Неподтверждённые опасные действия | Остановить пилот, оставить safety, разбор причины |

## 5. Артефакты, которые Codex должен оставить после текущей задачи

- Путь CLI прототипа и команда запуска (без секретов).
- Минимальная схема узлов и описание состояния LangGraph.
- Отчёт **по каждому сообщению** 5+2 разговоров (не только сводные оценки).
- Таблица сравнения с baseline и отдельный список ограничений сравнения.
- Следы/диагностика Qdrant и отсева документов без записи в базу.
- Стоимость/число Groq-вызовов и задержки, если реально измерены.
- Актуализация `docs/PROJECT_STATE.md`, при этом новый план не заменяет технический журнал.
- Список изменённых файлов, `git diff --check`, перечень реально выполненных тестов, отсутствие изменений production и состояние git.

## 6. Правило следующего действия

**Первый шаг уже выполняется.** По получении результата Codex: сверить факты с пунктами A–C, отметить `готово / частично / не сделано / blocker`, не переоценивать успех из-за тестов, не запускать новую архитектурную ветку автоматически. Следующее изменение выбирается строго по обнаруженному узкому месту. Перед каждым этапом читать `AGENTS.md`, `docs/PROJECT_STATE.md` и этот план; новые решения и результаты датированно фиксировать в `PROJECT_STATE.md`.
