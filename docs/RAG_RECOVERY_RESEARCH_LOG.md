# Журнал исследований восстановления RAG

Актуальные статусы этапов — в [RAG_MASTER_PLAN.md](RAG_MASTER_PLAN.md). Этот журнал сохраняет датированные наблюдения, включая отрицательные результаты и пределы доказательства.

Записи добавляются по мере проверки. **Факт** означает воспроизведение кодом или сохранённым trace; **гипотеза** не является выводом; **решение** описывает выбранное изменение; **непроверенное предположение** требует отдельного эксперимента. Секреты, персональные данные и production SQLite сюда не копируются.

## 2026-10-23 — P0.3: область действия отрицательного evidence

- **Исходная версия:** HEAD `7184eaa665004cd865f988cbb50b4f361eec6146` с незакоммиченными правками `docs/PROJECT_STATE.md` и `docs/RAG_RECOVERY_PLAN.md`; ранее выполненные P0.0–P0.2 присутствовали. Изменения документов до начала этой задачи сохранены.
- **Факт / симптом:** сохранённый baseline для поиска чека по ФД содержал `search_parameter_unconfirmed`, хотя approved-статья `platformaofd-lkk-receipt-search` прямо называет ФД и ФП. Детерминированный replay `_unconfirmed_search_parameters` вновь дал ложный gap. Сохранённый raw ответ модели тоже ошибался, но repair удалял этот claim; новый ложный вывод возникал при последующем формировании limitations.
- **Проверенные гипотезы:** (1) отсутствие релевантного источника — **опровергнуто** статьёй и trace; (2) отрицательная проверка собирает поле из предупреждения о подмене, а операцию из другой фразы — **подтверждено** вызовом `claim_supported` для положительного и отрицательного synthetic claim; (3) для ФН положительное доказательство берётся из отдельного поиска кассы — **подтверждено** существующим regression test, который сначала упал после первого исправления.
- **Причина:** `app/response_grounding.py::claim_supported` агрегировал совпадения по предложениям и при отрицательном claim мог связать разный subject и predicate. Для положительного поиска технический идентификатор проверялся вместе с любым другим словом, не обязательно с объектом поиска. `app/retrieval_pipeline.py::_unconfirmed_search_parameters` получал на этой основе ложный отрицательный proof.
- **Решение:** для перефразированного отрицательного утверждения требовать совпадающий subject до отрицательного predicate в одном source clause; операция и достаточное пересечение конкретных терминов также проверяются в этом clause. Дословная цитата source остаётся допустимой. Для положительной связи технического идентификатора с поиском требовать тот же объект поиска в clause с идентификатором. Необнаруженное поле остаётся `unconfirmed`, но не превращается в доказательство отсутствия функции сервиса.
- **Изменения:** `app/response_grounding.py`, `tests/test_p03_scoped_negative_evidence.py`. Отдельного правила для ФД/ФП в `_unconfirmed_search_parameters` не добавлено; общий validator сохраняет `claim_supported` и fiscal safety gates.
- **До/после:** до изменения FD state/context давал ложный gap; после исходный вопрос и две независимые формулировки ФД/ФП дают пустой список gap, ФН остаётся неподтверждённым. Два синтетических других домена проверяют перенос отрицательного вывода между ИНН/номером счёта и датой/статусом. Профильный прогон: 36 passed. Полный pytest первоначально: 306 passed, один побочный отказ на дословной role citation исправлен и повторно проверен (20 passed профильных), один импорт vNext остановлен отсутствующим бинарным модулем `uuid_utils._uuid_utils` в локальном `.local/vnext-deps`.
- **Retrieval benchmark:** read-only Stage3 `knowledge_stage3_retrieval_20261022`, 100 вопросов / 83 approved, expected context 81/83. Все 100 строк и агрегированные метрики совпали с `experiments/p02-benchmark-after.json`; результат в `experiments/p03-benchmark-after.json`. Это не проверка качества новых LLM-ответов.
- **Регрессии/ограничения:** первоначально слишком строгая обработка дословной отрицательной цитаты ухудшила тест role matrix; устранено без возврата cross-clause proof. `claim_supported` остаётся эвристикой, в том числе для иных идентификаторов без нормализованных metadata. Новых LLM-вызовов, индексации и production-записей не было.
- **Непроверенное предположение:** типизированные утверждения вида `(операция, объект, параметр, полярность, область применимости)` из reviewed metadata смогут заменить часть лексического proof. Требуются независимая разметка и holdout по нескольким категориям.
- **Следующее:** завершить P0.4 отдельно; после него провести полный регрессионный прогон и анализ P0.5/P1 без реализации.

## 2026-10-23 — P0.4: связь реплики с активной задачей

- **Исходная версия:** результат P0.3 в текущем рабочем дереве; изменения P0.3 и P0.4 проверялись раздельными тестами. HEAD остаётся `7184eaa665004cd865f988cbb50b4f361eec6146`, commit/push не выполнялись.
- **Факт / симптом:** `DialogueManager.advance` для «перестали загружаться выписки» → «1С:Бухгалтерия 3.0, подключение к банку через DirectBank» менял `bank_statement/diagnose`, `task:1` на `network/connect`, `task:2`. «Проверить срок договора» → «У меня Платформа ОФД. Распиши подробно...» менял `billing/check` на `unknown/check`. `build_rag_query` после обоих переходов терял исходную задачу.
- **Проверенные гипотезы:** (1) неверная сущность DirectBank — **опровергнуто**: `LexicalAnalyzer` извлекал software/integration; (2) существующий `new_task` из-за нового лексического intent/operation — **подтверждено** `LexicalAnalyzer.analyze` и переходом `DialogueManager.advance`; (3) любой ответ с entity надо безусловно присоединять — **опровергнуто** контрпримерами с новой командой, вопросом после приветствия и кодом ошибки; потребовалась граница речевого акта.
- **Причина:** именная конструкция «подключение к банку» интерпретировалась как команда `connect`; фраза с названием сервиса и просьбой «распиши...» получала operation `check`, после чего общий fallback `new_task` считал её самостоятельной. TaskContext хранил факты, но неверная relation уничтожала корень и symptom до retrieval.
- **Решение:** декларативная реплика с явно названной сущностью, без нового симптома/кода ошибки, вопроса, требования, явной смены темы или команды над другим распознанным объектом становится фактом активной задачи. Её текст входит в `details`, если это не одно название сущности; сам исходный intent/operation и symptom не перезаписываются. Явная смена темы, самостоятельный вопрос, новая неисправность и команда над другим объектом открывают новую задачу. Это ограниченное правило о relation, а не список сервисов или семи фраз.
- **Изменения:** `app/dialogue_state.py::LexicalAnalyzer.analyze`, `tests/test_p04_task_continuity.py`. Схема хранения не менялась. Подтверждённые сущности и `ExpectedClarification` продолжают обрабатываться существующим reducer.
- **До/после:** DirectBank и договор удерживают исходный `task_id`, operation и корень query; независимая банковская переформулировка и ответ об Эвотор проверены. Позитивные и отрицательные многоходовые сценарии покрывают ожидаемый сервис, явный новый вопрос, новый symptom, отдельную императивную команду, исправление сервиса и отсутствие банковских фактов в новой задаче. Профильный прогон после исправлений 65 passed; отдельный набор P0.4 — 9 passed. Полный pytest: **317 passed**, 13 deprecation warnings LangSmith. Для Python 3.14 только в игнорируемой `.local/vnext-deps` установлены совместимые колёса `uuid-utils`, `ormsgpack`, `xxhash`, `orjson`; исходники проекта и production-зависимости этим не менялись.
- **Retrieval benchmark:** read-only Stage3 на промежуточной версии P0.4: 100 вопросов / 83 approved, expected context 81/83, 2 прежних ошибочных отклонения, 0 новых item-level изменений против P0.3 и P0.2 на существующем наборе. `experiments/p04-benchmark-after.json`. После последнего уточнения границы самостоятельной команды benchmark не повторён из-за остановки работы. Набор в основном одноходовый, поэтому не доказывает качество многоходовых ответов.
- **Обнаруженная регрессия и исправление:** первое широкое правило присоединяло самостоятельный вопрос с приветствием, код ошибки и номерные повторные вопросы; full pytest указал три отказа. Условие сужено до декларативного сообщения без `?`, симптома, error code или императива над другим распознанным объектом. Повторный полный прогон прошёл.
- **Ограничения / непроверенное предположение:** лексический анализатор всё ещё ограничен словарём и поверхностным распознаванием речевого акта; для совершенно новых доменов уверенное различение исправления факта, новой задачи и косвенной просьбы потребует типизированного model-backed наблюдения с цитатами и детерминированным reducer. LLM-качество после P0.4 не измерено; клиентский результат улучшенным не объявляется.

### Наблюдаемые специальные правила, мешающие масштабированию

**Факты:** `procedure_policy.py::reviewed_safe_diagnostic_section` привязан к `bank_statement` и точному заголовку; `retrieval_pipeline.py::_related_search_task` и `_related_task_for_query` содержат пары категорий; `answer_service.py::_answer` содержит отдельные тексты для ЭДО, ФН и service clarification; `response_grounding.py` хранит частные role/technical checks; `vnext/cli.py::respond` имеет общий OFD fallback. Некоторые guards являются необходимыми safety-границами, поэтому замена допустима только после reviewed section/action metadata и holdout. Нельзя механически удалить все специальные правила.

**Решение для следующего этапа:** P0.5 начать с hash-bound frozen 15+3-turn A/B и ручной claim-level разметки после отдельного решения о новых Groq-вызовах. Отдельный подробный A/B-план и раздел целевой архитектуры ещё не подготовлены: работа остановлена по просьбе пользователя. P1.1 и P1.2 затем проектировать раздельно. Непроверенное предположение: typed state и scoped evidence достаточно уменьшат оба класса ошибок без новых ложных допусков; это требует E2E подтверждения.
