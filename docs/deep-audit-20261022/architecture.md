# Архитектура и параметры работающего тракта

## Границы системы

`bot.py` принимает Telegram-сообщения последовательно (`concurrent_updates=False`). Свободный диалог хранится в `data/conversations.sqlite3`; экспертное тестирование — в отдельной `data/evaluations/expert_reviews.sqlite3`. `ConversationStore.begin` сохраняет вопрос и резервирует ответ; `complete` сохраняет текст и весь `Answer` как `diagnostics_json`. Inline-оценки и заявки привязаны к ID этого ответа. Код и исходные диагностики находятся в пакете; обе исходные SQLite в пакет не включены.

## DialogueState и RAG query

`app/dialogue_state.py` применяет лексический анализатор к каждому сообщению. Он выделяет intent, operation, объект, сервис/производителя/оборудование/ОФД/ПО, цель, ограничения, параметры поиска и код ошибки. Каждый извлечённый факт имеет цитату и диапазон символов в конкретном клиентском сообщении. Состояние хранит `task_id`, границу темы, переход (`new_task`, `continue_task`, `clarification` и др.), ожидаемое уточнение и неопределённость. Ответ бота может открыть ожидаемый слот, но не становится подтверждённым фактом клиента.

`app/rag_query.py` собирает ограниченный 500 символами запрос из активного сервиса и операции, затем подтверждённых условий задачи. Для `report/view_reports` добавляется исходная формулировка клиента. Если связь сообщения с задачей не определена или запрос превышает бюджет, система запрашивает уточнение.

## Индекс, embeddings и hybrid retrieval

- Активная коллекция: `knowledge_sprint_v1_20261022_quality_gate`, 927 точек, 269 документов; Cosine, размер вектора 384. Запущен `RAG_DEMO_MODE=1`. **Все 269 документов имеют статус `draft`**. При обычной настройке `demo=false` фильтр `status=approved` исключил бы их.
- Локальная модель эмбеддингов: `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`; `SentenceTransformerEmbedding` нормализует выходные векторы. Векторы Qdrant включены в пакет. В ходе экспорта модель не запускалась.
- `DocumentLoader` обрабатывает Markdown, TXT, HTML и PDF; YAML front matter и sidecar метаданные дают ID, сервис, задачу, операции, статус и URL источника. `Chunker(max_chars=1200)` собирает параграфы по разделам и режет только слишком длинные части. Каждый chunk ID детерминирован от document ID и порядкового номера через UUID5. Отдельного overlap в этом chunker нет.
- `Retriever` читает доступные точки, получает dense top-k из Qdrant и считает BM25 по тексту чанков и заголовкам. Лексические токены нормализуются, есть небольшой словарь расширений. Точные числовые коды, бренд и модель ограничивают кандидатов. Итоговый RRF: `2/(60+bm25_rank) + 1/(60+dense_rank)`. Номера списка в начале клиентского вопроса исключаются из точного числового фильтра.
- `RetrievalPipeline` запрашивает до 100 кандидатов, дедуплицирует по документу, проверяет сервис, производителя/модель для технических задач, category и operation. До 5 документов расширяются соседними чанками; контекст ограничен 7000 символами. `sufficient` обычно требует подходящего документа с оценкой task fit не ниже 0.62. Для access-процедур дополнительно проверяются конкретные шаги и `evidence_coverage`; подтверждённые части могут быть отданы при неполном покрытии. Причины отклонения и score сохранены в `retrieval_diagnostics`.
- Web fallback, reranker и GraphRAG в рабочем тракте не включены. Исходный материал остаётся `draft`, даже если факты в нём совпадают с официальной справкой.

## Генерация и проверка

`app/answer_service.py` сначала решает, нужен ли сервис или уточнение, выполняет task-aware retrieval и может вернуть подтверждённую часть без LLM. При недостаточном evidence для конкретных операций срабатывает ранний `no_context`/эскалация. Для отчётов АТОЛ по замене ФН действует узкий extractive-ответ по карточке `atol-online-account-cash-reports`; общий вопрос получает ограничение области источника.

При генерации сообщение содержит `SYSTEM_PROMPT` из `code/app/answer_service.py`, RAG-контекст, типизированные факты активной задачи и текущий вопрос. Предыдущие ответы модели не повышаются до фактов клиента. Действующий провайдер — Groq, модель `openai/gpt-oss-20b`, `reasoning_effort=medium`, `temperature=0.2`, `max_completion_tokens=2048`; HTTP timeout 90 секунд. Точные системные инструкции, JSON-сценарии `answer|clarify|escalate` и формирование user prompt доступны в кодовом снимке.

Validator в `app/answer_service.py` и `app/response_grounding.py` проверяет опасные фискальные действия, названия UI, роли и полномочия, подтверждение сервиса, конкретные технические утверждения и шаги. Неподтверждённые части могут быть заменены извлечёнными фразами источника либо безопасным ограничением. `validation_status`, `validation_reason`, исходный модельный текст, repair, токены и факт попытки LLM сохранены в диагностике, если были доступны. Отказ валидатора и недостаточность retrieval — разные причины и должны анализироваться отдельно.

## Сохранение обратной связи

`feedback_events` фиксирует конкретное нажатие; отчёт считает последнюю оценку каждого ответа. `support_requests` связывает разговор, исходный вопрос и ответ, проходит `pending_confirmation → saved`. `escalation_events` сохраняет действия и краткую retrieval-сводку. Реальный канал доставки специалисту отсутствует: `saved` не равен `delivered`. Неоценённый ответ не считается успешным.
